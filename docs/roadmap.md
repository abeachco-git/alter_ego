## Application-wide consistency audit — Part 4 (proposed)

Remaining packages are discussion only and require separate explicit approval. Reuse the current comparison, exact-identity and activity-scheduler foundations; this is not a blanket refactor. Findings below are source-level evidence, not completed runtime fixes.

### D1 — Functional equivalence and recognition (high impact; medium/high risk)

- [ ] **D1.1 — Canonical comparison primitives.** Consolidate valid utility-ID multiset normalization in `BuildCompareCore.h`, `ComposableLoadouts.h` (ReuseKey) and `ComposableSemantics.h` (SkillBar). Preserve heal/elite positions, utility multiplicity, terrestrial/aquatic separation, profession context, unknown extensions and original payload order. Audit call sites before retiring unused normalization helpers. Keep exact fingerprints/content, reference identity, functional equivalence and directional requirement satisfaction separate; only exact compatible content can be reused or merged by existing storage rules.
- [ ] **D1.2 — Evidence and unknowns.** Detailed Compare builds typed verdicts but its utility row uses a combined display string; template classification tests the literal "(empty)", which misses a zero inside a combined utility list. Unresolved negative trait choices are skipped; absent weapon/relic metadata can omit required rows. Emit typed Match/Different/Unverified evidence for required fields, rather than inspecting labels or treating skipped rows as success. Discuss recorded empty vs omitted/unretrieved skill/gear data and optional aquatic requirements; do not infer presence from legacy zero defaults. Preserve the skills-only warning for fully verified non-skill/gear matches; include heal/elite and aquatic skills in accurate wording. Stat comparison currently can pass a display-only "#ID" fallback as a name, creating a false mismatch against resolved metadata. Use actual canonical names/IDs/attribute evidence. Current stat metadata has attribute names, not amounts: compare stat selection, not exact numerical bonuses; no new metadata schema/fetch work in this package.
- [ ] **D1.3 — Aquatic comparison coverage.** `CalculateSavedVsLiveComparison` still aggregates only six terrestrial runes and four terrestrial weapon slots for sigils. Aquatic owns its own upgrades. Compare configured aquatic helmet rune in the underwater configuration (replaces terrestrial helm, never seven runes); compare each aquatic weapon's sigils independently; route aquatic stats, type, rune, sigil and slot infusion rows to Aquatic. Normalize saved/live aquatic slot aliases for lookup without altering stored keys; validate exact equipment-tab/shared relic rules. Missing optional aquatic components must not prevent a terrestrial match; partial recorded requirements must remain visible and not imply full verification. Reuse existing configuration and slot helpers, preserve physical capacity and multiplicity.
- [ ] **D1.4 — Infusion and upgrade requirement semantics.** Detailed Compare already uses `InfusionMatchCore.h` and configuration totals; legacy component similarity summarizes counts without full presence, attribute-only slot or topology evidence. Reconcile advisory similarity with canonical typed semantics; remove or suppress misleading hints where not provable. Preserve exact versus attribute requirement, recorded empty versus absent, slot-mode placement, and directional numerical minimums (AR cap 150, separate terrestrial configurations). No silent mode conversion, no pooling alternate weapons/aquatic gear, no automatic component reuse on functional match. Keep known slot mismatch separate from aggregate infusion warnings in active recognition; check the existing misleading comment about slot infusion exclusions.
- [ ] **D1.5 — Shared recognition and ranking evidence.** Characters active recognition, detailed Compare and automatic saved-build suggestion already invoke the same comparison function, but independently classify/rank and cache it. Extract reusable typed field/coverage results and distinguish template equivalence from candidate preference; preserve explicit/manual selection, source-character preference where intentional, exact-ID acquisition opt-in and verified personal stock boundaries. Replace or reconcile the active matcher’s second metadata/coverage pass and raw saved/live slot-count completeness check; use canonical expected-slot evidence with optional groups, without changing full-match policy silently. Review auto suggestion scoring and its treatment of unverified vs mismatch; keep suggested candidate separate from verified match. Include resolved Equipment Set references in section identity/coverage. Check account+character identity, selected/active build and equipment tabs, revision and metadata arrival invalidation across all three consumers (detailed cache has 500 ms metadata fallback while active recognition and auto suggestion only key on revisions); reuse existing immutable metadata/revisions or bounded local reevaluation, never trigger extra HTTP. Retain original stored payload and all exact edit/revision safeguards.
- [ ] **D1.6 — Regression and scoped cleanup.** Extend existing build comparison, composable, native library/editing, infusion and navigation suites: all utility permutations/duplicates, unknown vs empty, unresolved traits/stats, aquatic aliases/configurations and optional gear, rune/sigil scope and counts, infusion modes/attributes/minimums, ranking/metadata arrival, stable reference identity and exact round-trip. Audit related exact-reuse/recognition call sites without reopening the unrelated inherited editing or naming decisions. Test independently and deliver a verified DLL before closing D1.

**D1.5 design clarification (proposed package; implementation approval still required):** Characters presents compact configuration-health summaries, not field-level Compare details. Expected (explicit character assignment or automatically inferred candidate), matched (verified functional equivalence) and detailed comparison are separate concepts using the same typed evidence. Persist Automatic / None / explicit stable Loadout ID against exact account and character identity, independent of in-game build/equipment tab numbers. Active tab contents are observations to compare, never assignment authority; equivalent contents in different tabs match, and changing or browsing tabs must not change the expectation. Profession-compatible compact Loadout selector near Save/Share; reuse existing controls, shared contextual Compare/Open in Library actions, reset/disable actions and navigation. Explicit expectations never silently switch to a better match; deleted or invalid references fall back safely to Automatic. None suppresses recognition warnings. Automatic may show credible near-match warnings but never label an unverified suggestion a match. Group actionable warnings by category; collapse two or more distinct affected child categories into Check Build or Check Equipment as appropriate, retain single-category warnings, independent aggregate infusion warnings and optional aquatic semantics. Keep detail in tooltips/Compare; preserve active-only recognition scope and existing freshness behavior. Extend persistence, stable-reference, account isolation, tab mismatch, navigation and summary regression coverage. Determine the smallest compatible preference-storage design before implementation; no change to authoritative Loadout payloads or storage identity.

### D2 — Freshness and status policy consistency (high impact; separate approval)

- [ ] **D2.1 — Policy vocabulary and durations.** `RefreshEngine.h`, `CharacterActivity.h`, `CharacterScopes.h` and `NativeInventoryCore.h` distinguish observation freshness from eligibility. Map scope names and canonical durations in one policy location where safe (10-minute character and Bank/shared/material scopes; 30-minute Armory and ordinary time-based inventory; 24-hour roster; 15-minute ordinary failed-attempt cooldown, 0–45-second recurring spread). Existing activity-based routing is correct in principle; generic 30-minute fallback is not proof of a regression. Do not mechanically replace NativeInventory::Due with RefreshEngine::Due: their successful/failed-attempt guards differ. Preserve exact boundary behavior, logout grace, specialization debounce, independent scope coverage, manual bypass and demand gates.
- [ ] **D2.2 — Read-only scheduler inspection.** Share a typed snapshot/description for per-scope freshness, last success/attempt, failure, permission/ownership, enabled policy, eligibility reason/time and actual pending/working state. `DescribeCharacterRefresh` and Inventory footer duplicate wait-reason labels/durations; Inventory eligibility uses a separate permission gate from the footer. Show permission-denied or unverified ownership instead of claiming eligible/scheduled, distinguish no successful data from stale retained data, and use one sampled clock per inspection. Preserve separate account/character keys, existing scheduler decisions and no requests/SQL on inspection. Do not expand to metadata, Wiki, objective or transport scheduling.
- [ ] **D2.3 — Status presentation and aggregate scope.** Reuse RefreshUI for consistent labels/severity (neutral current/scheduled/propagation/stagger, amber retry countdown or stale auto-disabled, actionable error/denied, spinner only when work is actually pending/active with accurate wording). Inventory currently labels cooldown "Retrying" while idle; character stale status can replace a real error with neutral scheduling. Retain last confirmed success and oldest complete required-scope timestamp; partial/failed retrieval never advances it. Distinguish unavailable vs empty vs no scopes, no API vs denied, cached stale vs failed; preserve independent price diagnostics, grouped progress, deduplicated character logout countdown, visible-scope and manual-refresh behavior. Compare footer currently resolves target by name separately: audit reuse of the exact account/character target and completion attribution rather than global/name-only status. No new automatic refresh or scheduling change without separate approval.
- [ ] **D2.4 — Regression and scope fence.** Add deterministic fixtures for interval and retry boundaries, future timestamps, login/logout grace, stagger, specialization changes, offline unchanged data, partial successes, permission/auto-off, in-flight vs cooldown, scope-specific error and aggregate timestamps; compare status projection against existing admission/eligibility. No new HTTP, no per-page lifecycle, transport, cache, persistence or objective reset refactor. If a behavioral scheduler defect is found, document it and obtain specific approval before changing it. Test independently and deliver a verified DLL before closing D2.
