### Part 2 — Equipment, skills and build editing primitives (high impact, high risk)

- [ ] B1. Consolidate full Loadout and standalone Component gear editor behavior using typed editing primitives/adapters and existing catalogs, GearEditCore, EquipmentChoiceCore and ComposableGearPresentation. RenderGearEditContext currently offers typed field-specific copy/paste, clear, and propagation; ComponentNativeGear independently copies JSON fields and supports different compatibility/propagation options. Reuse compatible slot/stat/weapon/rune/sigil/relic/infusion controls and operations, preserve capacity and valid slot constraints, explicitly absent versus unknown data, exact IDs, imported fields and component-specific boundaries. Do not merge private/shared commit paths. Evidence: src/dllmain.cpp (RenderGearEditContext, RenderGearCustomizeDialog, RenderBuildGearPanel), src/ComposableNativeEditor.h (ComponentNativeGear, catalog/stat/weapon/infusion functions).
- [ ] B2. Consolidate skill picker grid, anchor/close handling, icon selection/highlight, clearing and duplicate-utility swaps. Both editors already share SelectableBuildSkillIds and skill icon rendering, but have separate pickers and mutation code. Full Loadout skill picker currently writes terrestrial AND aquatic bars; standalone Skills edits them independently. Discuss explicit aquatic policy before changing either. Review specialization/trait, Ranger pet and Revenant legend pickers for similar reuse opportunities; retain profession, specialization, aquatic and missing metadata constraints. Evidence: src/dllmain.cpp (RenderSkillPickerDialog, RenderSpecPickerDialog, RenderLegendPickerDialog, RenderPetPickerDialog), src/ComposableNativeEditor.h (ComponentNativeSkill, ComponentNativeSkillBar, ComponentNativeSpecializations).
- [ ] B3. Align field-level context actions and edited slot summaries for supported fields. Reuse existing icon, tooltip, name-copy and clipboard primitives. Internal typed gear/component clipboard and portable external clipboard have different purposes; do not indiscriminately unify formats or allow incompatible pastes. Never use direct Windows clipboard or bypass the Nexus/ImGui native input path.

Acceptance discussion: identical edit behavior for equivalent fields, private/shared draft isolation and explicit Save review, exact round-trip preservation, clear/copy/paste/slot capacity and utility swaps, independent aquatic decisions, and no new per-frame requests. Split B1 and B2 into independent implementation batches if needed.

### Part 3 — Search, hierarchical browsing and catalog presentation (high/medium impact, low/medium risk)

- [ ] C1. Extract a shared search normalization/tokenization/matching policy from existing SkinSearchCore and UI catalog matcher. Inventory and Skinventory already share token/fuzzy matching; Characters, Loadouts, Equipment Sets, Fashion, Achievements and gear catalogs use independent case-insensitive matching. Discuss which screens should use multi-token AND, typo tolerance, exact IDs or literal substring; preserve searchable fields and the deliberate three-character search-first List rule, Groups browse-first behavior, filters/chips and no query-triggered requests. Avoid blanket change in result semantics. Evidence: src/SkinSearchCore.h, src/UIControls.h (CatalogMatches), src/dllmain.cpp, src/ComposableUI.h, src/FashionModel.h.
- [ ] C2. Reuse stable group identity, flattening/clipping, explicit expansion persistence, temporary search expansion, selection reveal and contextual hit targets from Inventory Groups for applicable grouped lists. Components/Loadouts use separate collapsible heading logic; Guild Bank uses native tree nodes. Extract generic behavior where valuable, not Inventory-specific ownership semantics. Preserve character sorter, custom drag/drop, semantic group ordering and CompletionTheme for specialized Achievements/Clears. Evidence: src/InventoryGroupCore.h, src/CatalogPresentation.h, src/ComposableUI.h, src/dllmain.cpp, src/NativeAccounts.cpp.
- [ ] C3. Extend catalog row/presentation reuse to dedicated Wallet and Guild Bank where appropriate: Wallet hand-draws icon, pin and balance rows; Guild Bank separately aggregates rows and displays plain rarity text without standard item icons. Discuss icons, quantities, alternating backgrounds, clipping, selection/details and context actions. Preserve currency pins/order/coin formatting, guild access and globally shared stock, item aggregation and account ownership boundaries. Do not include guild stock in personal acquisition or sale estimates. Evidence: src/NativeAccounts.cpp (RenderInventory, Wallet/Guild Bank branches), src/CatalogPresentation.h.

Acceptance discussion: predictable search and filter behavior, stable selected rows, correct quantities and contexts, visible groups and search reveal, native click/release/scroll behavior and large-list performance. ArcDPS overlap click issue remains separately tracked; never work around host input routing.

### Part 4 — Functional equivalence and status policy consistency (high impact, high risk; separate approval for each)

- [ ] D1. Audit and consolidate functional comparison definitions for skills, stats, runes, sigils and infusions. Detailed Compare uses CanonicalUtilityIds; Composable::ReuseKey and Composable::Semantics::SkillBar normalize utility order separately. The visible policies broadly agree for valid utility IDs; no confirmed mismatch is asserted. Review saved/active recognition, exact item acquisition hints, component similarity/reuse and missing data. Heal/elite remain position-specific, utilities unordered with multiplicity, terrestrial/aquatic independent, and original payload order preserved. ExactContent and reference identity remain separate from functional equivalence; never auto-merge saved components merely because requirements match. Include the remaining skill recognition-path audit in D1; do not create parallel semantic engines. Main Compare utility permutation regressions already exist. Evidence: src/BuildCompareCore.h, src/dllmain.cpp (compareSkills), src/ComposableLoadouts.h (ReuseKey), src/ComposableSemantics.h, src/NativeLibraryEditing.h.
- [ ] D2. Audit remaining freshness/status presentation and policy duplication separately from UI work. NativeInventoryCore defines generic TTL/retry constants while ActivityScope routes Bank/Bags/Equipment/Shared inventory/Materials/Armory through CharacterActivity/RefreshEngine. The approved 10-minute mutable-storage policy and 30-minute Armory policy are in use; generic 30-minute constants do not prove a regression. Discuss canonical duration definitions, freshness vs request eligibility, stale/failed/pending/denied/unknown presentation and RefreshUI diagnostics. Preserve 0–45-second staggering, 15-minute failure cooldown, propagation grace, visible demand and manual bypass. Objective, Wiki and metadata broker work is already tracked elsewhere; do not pull it into this pass. No scheduler, retry, lifecycle, transport or persistence changes without specific separate approval. Evidence: src/NativeInventoryCore.h (FreshSeconds/Due), src/NativeAccounts.cpp (ScopeFresh/ScopeDue), src/RefreshEngine.h, src/CharacterActivity.h, src/RefreshUI.h.

Acceptance discussion: regression fixtures for equivalent and different builds, unknown/absent data, stable exact identities; status labels and actual scheduling agree, no extra HTTP. Keep D1 and D2 separately approved and tested.

### Boundaries and review workflow

- Preserve established visuals unless explicitly redesigning, stable Nexus ImGui 1.80 ABI, existing native hit targets, thread ownership, bounded inputs and host clipboard callbacks. No migration/schema change, request expansion or release/updater modification as incidental cleanup.
- Reuse the existing foundations: UIControls, CatalogPresentation, CharacterOrderCore, EquipmentLayout, CompletionTheme, RefreshUI, NavigationUI, StoragePaths and NativeInventoryCore. Do not mechanically eliminate direct ImGui calls or force specialized rows into one layout.
- Before implementing any package, present evidence, exact proposed changes, deliberate exceptions, unresolved behavior decisions, dependencies, risk and regression checks. Ask for approval of that package only. Update this tracker as work is approved; prune completed items after required automated verification and retain remaining validation in development-status.md. Do not mark discussion as implementation.
- After an approved implementation, follow AGENTS.md definition of done, including exact-commit Windows build and verified DLL delivery. Live/in-game validation is separate and must be reported honestly.

Recommended remaining Part 1 discussion/delivery order: 1C shared commands/action availability, then 1D dialogs and global-sort navigation. Both require separate approval.
