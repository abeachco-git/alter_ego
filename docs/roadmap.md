# Future roadmap — native account inventory and Hoard & Seek integration

Status: proposed, not implemented. Source audit: [Hoard & Seek v1.1.0.0](https://github.com/PieOrCake/hoard_and_seek/tree/v1.1.0.0) (MIT, retain copyright and license notices). The user is beginning actual in-game debugging of composable loadouts; prioritize stabilization and the existing eleven workstreams in [development-status.md](development-status.md). Do not start this larger project or create/merge a branch until explicitly approved. Suggested future branch: `experiment/native-account-inventory`, based on the stabilized experimental code.

## Goal and architecture

Make native authenticated account access and inventory available within Alter Ego without requiring a separate Hoard & Seek DLL. Integrate functionality rather than wholesale copying its addon, UI, caches or lifecycle. Keep native and external providers behind a typed service boundary; optionally offer a separate compatibility bridge for third-party H&S clients. Never allow two providers to answer the same H&S request; default to a single explicit provider and test coexistence, switching and unavailable-provider behavior. Internal callers should not route through the compatibility event bridge. Preserve upstream compatibility and Nexus ImGui 1.80 ABI.

## Proposed phases

1. Audit authenticated endpoint consumers and H&S contracts. Add native account/key management with validated account identity and permission scopes, DPAPI-protected durable credentials, explicit account selection (no implicit first-account fallback for scoped requests), redacted diagnostics, strict HTTPS hostname/certificate validation, bounded cancellable requests, rate limiting/429 backoff, fair bounded queue, in-flight deduplication and typed request IDs/results. Reuse existing owned workers and callback gate. Do not cache failed HTTP/JSON results as successes. Never expose credentials through diagnostics, cache exports or generic external proxy.
2. Implement provider interface for native and external H&S operation. Migrate existing character, roster, achievement, Vault, Clears, skin/recipe/mastery and item-location consumers incrementally; retain existing refresh behavior and no network activity from ordinary rendering/search/filter. Validate account, endpoint, request generation and permissions; reject stale completions.
3. Add relational inventory repositories in rebuildable cache.db (schema version to be chosen when implemented). Reuse reference_items, shared metadata and character equipment; avoid duplicate data and opaque JSON blobs. Typed inventory snapshots, slots, wallet balances, currency metadata, guild GUID/membership/storage, legendary armory. Store exact account, character, scope and slot identity, count, binding, freshness, completeness, and relevant item-specific data. Handle bank, material storage, shared inventory, character bags/equipment, guild stash, delivery box, wallet and armory. Account and guild access must be scoped; deduplicate guilds by GUID, not name. Distinguish successfully empty from skipped, failed, denied and unknown; preserve previous successful scope on failure, publish atomic scoped commits and immutable snapshots. Distinguish legendary ownership from equipped references, wallet from items, and accessible stock from guild/delivery/equipped/bound stock. Keep configuration/refresh exclusions outside rebuildable cache. No render-time SQL. Revisit journal/connection policy only with measurements.
4. Add explicit, non-destructive import of H&S account labels, refresh preferences, cache data and credentials if authorized, validating identity and schema, retaining original files, and avoiding plaintext secret copies. Migration is optional; support rebuild from API. Include Storage & Cache diagnostics, selective recovery, and backup/restore rules. Retain localized names and optional Decoder Ring integration with English fallback.
5. Build Inventory primary tab with shared UI::SearchToolbar, removable chips, search x, clear filters, stable sorts, compact expandable item rows, exact location details and freshness indicators. Allow empty-query browsing; substring/token/typo matching, item-ID lookup, localized/English names and accent/case normalization. Filters: account/current account, storage location, character, rarity, item type/subtype, armor weight, weapon type, level, binding, quantity, tradeability, freshness; show only relevant filter controls and preserve compatible selections. Suggested subviews: all items, materials, wallet, bank. Sort by name, quantity and relevant metadata; optional favorites. Right-click copy name/chat link, open wiki, view locations, navigate to character/equipment. Use immutable cached search snapshots, debounce if necessary, reject stale search generations, no fetch on typing/filter/sort. Group quantities accurately by selected scope.
6. Optional external H&S-compatible event adapter: preserve supported API versions, request/response ownership, permissions and context menu hooks, test ABI/payload bounds, provider conflicts and unload. Audit default access policy and least privilege before exposing authenticated endpoints. Native operation need not use legacy fixed-size reply buffers.
7. Cross-feature enhancements: compare loadout missing items against accessible account inventory with location links; Skinventory/shopping subtract owned usable acquisition items and show remaining cost; legendary material and currency requirement tracking; wallet favorites/categories; account-wide unused ascended gear/upgrade finder. Avoid claiming items are interchangeable or available when binding, stat selection, legendary reuse or stale/incomplete inventory prevents certainty.

## Source audit cautions

Do not port detached threads, raw unlocked metadata pointers, TLS hostname-validation bypass, plaintext key persistence, broad JSON rewrites under locks, coarse account-wide clearing on partial fetch, stale search publication, guild name-based deduplication, or success without HTTP validation. Adapt the useful token-bucket/backoff and selective refresh ideas, not the implementation unchanged. Source references: [GW2API.cpp](https://github.com/PieOrCake/hoard_and_seek/blob/v1.1.0.0/src/GW2API.cpp), [dllmain.cpp](https://github.com/PieOrCake/hoard_and_seek/blob/v1.1.0.0/src/dllmain.cpp), [ProxyThrottle.cpp](https://github.com/PieOrCake/hoard_and_seek/blob/v1.1.0.0/src/ProxyThrottle.cpp).

## Acceptance

Unit/regression coverage for account switching, late responses, permission failures, cancellation/unload, rate limits, complete-empty vs failed/partial scoped snapshots, guild dedup, legendary counts, filtering/sorting and stale search generation, cache reset and non-destructive migration. Validate native/external compatibility in game, including multiple accounts; preserve all existing CI gates and produce a verified Windows x64 UCRT DLL. Benchmark startup, refresh request counts, database size, search latency, and DLL size against the stabilized baseline; no performance or size target is claimed as measured today.
