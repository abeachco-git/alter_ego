# UI component reference

This is the discoverable source of truth for developers and coding agents. Read it before editing any UI. Preserve the current visuals and behavior: reuse is the goal, not blindly restyling every widget.

Nexus Appearance > Window Transparency is an additional 0–80% background transparency, default 0% (existing theme). Persist `window_transparency` in settings.json on slider release or reset; bound loaded values. Ordinary main, modeless editor, toast and tracker windows and child panels use `UI::BeginWindow` / `UI::BeginChild`, scaling their current theme background alpha only. Native popups, modal confirmations, tooltip windows and their child panels retain current theme opacity. Do not change global style alpha, controls, text, artwork, title bars, input behavior or the host style. New ordinary window/child consumers use these same helpers.

## Example
```cpp
if (RenderActionButton("Edit##item")) StartEdit();
if (AlterEgo::UI::BeginCombo("##choice", current.c_str())) {
    for (const auto& option : options) {
        ImGui::PushID(option.id.c_str());
        if (AlterEgo::UI::SelectableOption(option.name.c_str(), option.id == selected))
            selected = option.id;
        ImGui::PopID();
    }
    ImGui::EndCombo();
}
AlterEgo::UI::InputTextWithHint("##search", "Search...", searchString);
if (AlterEgo::UI::Button("Delete##item", ImVec2(0,0),
                        AlterEgo::UI::ButtonRole::Destructive)) OpenConfirmation();
```

Use stable IDs (not a display name or mutable row index when a persistent ID exists). Keep actions separate from display, and invoke the same domain action from header and context menu. Defer destructive changes until safe to mutate the collection.

## Intentional exceptions and remaining work
- Standardize refresh button appearance and layout using UI::Button / RenderActionButton and UI::ActionButtonHeight. Preserve the existing disabled state, click handlers, request execution, scheduling, timeouts, retries, caching and page-specific state. Do not consolidate request logic without explicit approval.
- The existing custom Cut/Copy/Paste/Select All menu lives in lib/imgui/imgui_widgets.cpp InputTextEx and inherits the active GW2 theme (popup background, hover/active colors, padding and typography). Preserve the theme and existing native text selection, UTF-8 filtering and callbacks. Test clipboard in game; do not add a wrapper popup or change ImGui version.
- Custom draw-list cards, roster rows, raid encounter chips, drag targets, and selected/active markers can have different geometry. Reuse palette and meaningful primitives; don't replace specialized rendering solely to remove raw calls.
- Equipment and independent component editing still have different storage and commit paths; shared catalogs and presentation helpers are the starting point. Further consolidation must preserve slot count, unknown vs absent metadata, exact IDs, copy-on-write and shared-component semantics. Do not claim all editor behavior is unified.
- Saved loadout header and context menu share ExecuteSavedLoadoutAction and RenderBuildShareMenuItems. The developer-only `BuildRelay::Enabled` flag in `src/BuildRelayPolicy.h` controls legacy one-time-code sharing, import guidance and relay dialogs; never add a separate GUI flag. Library row and header actions use their record-specific handlers (ExecuteSavedLoadoutAction, RunComponentAction, RunEquipmentSetAction, RunFashionAction). Keep specialized domain logic and caller-owned commits separate.
- Validate at different fonts and window widths, ensure popup focus and right-click work, and verify DLL compilation/artifact for the exact commit.

## Skinventory
- `RenderSkinContextMenu` in dllmain.cpp is the single skin menu; scope each popup to the stable skin ID. Skin links use `ChatLink::EncodeSkin`; actual TP item names and links come from the winning price candidate, not the skin name. Use `CopyToClipboard`.
- `SkinSearchCore.h` provides shared token/substring/typo search and price selection. Shopping filters operate on cached results and preserve the table sort; do not trigger price queries on typing or filtering.
- Commerce v2 derived cache retains all known tradeable equipment/skin-unlock candidates and names, selects the cheapest available sell listing, and does not reuse legacy rarity-selected prices. Vendor coverage remains limited to known cultural armor prices.

- Keep cached shopping candidate metadata and sort keys separate from local filters. Never scan or reprice all candidates per keystroke. Price snapshots are returned by value under the Commerce lock. A failed price batch must not publish a partial winner as the cheapest.

- Preview in Game is optional, using existing `PieUI_PreviewChatLink` when Pie UI is present. Its documented native action supports skin links (see https://github.com/PieOrCake/pie_ui/blob/master/INTEGRATION.md).

## Search and filter conventions
- `UI::SearchField(id, hint, query)` supports fixed char arrays and std::string; themed input, stable ID, clear-query button and width-aware layout. Use it in plain lists and searchable pickers, not ordinary edit fields.
- `UI::SearchToolbar(id, hint, query, collectFilters, drawFilters, resetFilters, optionalActionLabel, optionalActionClicked)` is the canonical compact toolbar for lists with filters. `collectFilters` returns `UI::FilterChips`: each active chip has a stable ID, display label and a remove callback that clears only that filter. A required default scope may have an empty callback, is shown as context, and is not counted. Count and chips derive from the same state. Chips wrap at narrow widths and each has a visible x; Clear all resets filters only. Search x clears query only. Popup body and reset are caller-owned; optional action returns a click, never executes a request itself.
- `UI::FilterChoice` provides consistent enum and string choices. Use specific descriptive filter labels and sensible default values. Only expose relevant controls, show active values, and retain existing persisted options, sort, and selection behavior. A required category or view preference can be displayed as context without pretending to be a search match.
- Characters and global Achievements use SearchField (sort and category-scoped completion visibility are separate); Loadouts, Fashion, Components, Skinventory Browser and Shopping use SearchToolbar. Gear stat/upgrade and component picker searches use SearchField. No raw per-page search input rendering; preserve ImGui clipboard context menu. Use `SearchCore.h` for prepared case-insensitive token AND matching, optional bounded one-edit typo tolerance for longer ASCII tokens, and exact numeric catalog IDs distinct from label text. Preserve UTF-8 bytes, domain-owned searchable fields, and existing browse/search thresholds; Inventory selection remains while the typed identity matches. Loadouts include cached profession/specialization names; query preparation and matching do not initiate dataset requests or change refresh lifecycles.

- Optional toolbar actions use standard action-button height; the adjacent search and filter controls align to that height without changing popup styling. Never make a refresh button an exception to shared button styling.

- Individual filter removal must preserve other compatible filters, search text, sorting and view settings. Skinventory Shopping marks only its local filter results dirty; no price refresh. The Browser ownership chip resets to All without changing list/grid. Component kind chips remove only that kind; an empty set means all categories. Preserve compatible selection. Keep both Skinventory views and all other filter toolbars in sync through `RenderFilterChips`.

## Canonical-control guardrails

- Preserve dropdown active/auto semantics and keyboard navigation; always pair a successful BeginCombo with EndCombo.
- Use existing profession/rarity helpers and named palette/indicator primitives instead of new per-tab colors or size constants. Use RenderGoldButton, RenderChipButton and the shared button roles according to their established meanings.
- Full Loadout and standalone Component editors share stat and upgrade catalog choices, typed equipment field clipboard and compatible copy/clear primitives. Exact-slot JSON copy stays same-category/same-position; configuration paste never overwrites unrelated imported fields. Unknown physical capacity does not justify filling hypothetical sockets. Keep commit paths appropriate to the underlying data.
- Aquatic is an optional first-class equipment component containing underwater headgear and both weapon positions, including per-slot upgrades. Existing v4 libraries are backed up and rebuilt transactionally, preserving exact Loadout projections and terrestrial component IDs. Mixed partial Equipment Sets retain combined aquatic configuration directly on their Loadouts. Bulk armor/weapon/infusion operations include compatible configured aquatic slots without creating missing aquatic slots. Legacy aliases remain exact.
- Loadout and standalone Skills use the same field-scoped native skill picker and utility swap operation. Base Build and Loadout editors share specialization selection; independent Pets and Legends components and Loadout editors share profession-specific pair controls. Both environments have independent pairs; cached pet/legend eligibility by environment is not verified. Clear and selection affect only the selected terrestrial/aquatic bar; the Loadout aquatic bar is collapsible. Preserve missing imported fields on inspection and the existing profession/spec context. Individual cached skill NoUnderwater evidence may restrict new aquatic skill choices; missing flags remain unknown. Do not infer whole-companion underwater eligibility.
- All skin surfaces use RenderSkinContextMenu. The selected Commerce candidate is based on available sell listings, never rarity; copy the actual priced item's name for Trading Post search.
- Every active contextual filter must have a stable removable UI::FilterChip with its own reset callback, except required default context. Clear all preserves search text; search x preserves filters. Both Skinventory views use the shared toolbar and chips. Preserve sorting and compatible selections; changing filters does not refresh prices or make API requests.
- When a shared control changes, update this guide and migrate affected callers where the scope allows. Preserve established appearance unless a redesign is requested.

### Library commands
Use grouped native context menus in this order: creation (New/Paste), editing (Edit/Rename/Duplicate), clipboard/sharing, specialized operations, and destructive Delete last. Separate nonempty groups with native ImGui separators. UI::MenuAction supports an optional concise enabled-action hover description and a separate disabled-reason tooltip; UI::MenuAction and UI::BeginActionMenu draw original font-responsive vector icons within the native menu row; no icon font, textures, downloads, input overrides or new dependencies. Header buttons invoke the same handlers and share availability predicates; use UI::AvailableActionButton for disabled actions and explain why. Unsupported actions are omitted. Right-click selects the stable record when no draft would be displaced. Empty-space creation uses the same action as the row menu; Equipment Sets have no portable Paste format.
Copy means clipboard data, Duplicate creates a new independent saved record, Rename changes only its name. UI::RenderNameAction owns only the name form, with caller-owned target/baseline and commit; default duplicate name is Original Name - Copy, cancellation creates nothing, and rejected saves retain the draft. Native Loadout duplication retains component/Equipment Set/Fashion references, Equipment Set duplication retains component references, Component duplication preserves exact independent payload, and Fashion duplication preserves appearance/provenance/metadata without copying incoming Loadout references. Explicit duplicates never auto-consolidate. Preserve collection-specific name validation. Create Separate Set and Make Private & Edit remain distinct reference-changing operations.
Fashion New/Paste use existing Wardrobe Template validation and editor; do not auto-save imports. Referenced Fashion may be deleted only after explicit Delete & Detach review of affected Loadouts and transaction-time revalidation of the reviewed owners; their functional build data is unchanged. Referenced Components and Equipment Sets remain protected. All copies use the native host clipboard.
 
### Library persistence terminology

Use Loadout Library, Components, Fashion, Import Library and Export Library. JSON is a portable interchange format, not the runtime storage model. Keep the existing combined equipment editor and independent component editors; save a draft through native commands and never mutate persistent state from presentation enrichment. Selective restore includes required Fashion dependencies and creates recovery snapshots before replacing data.

The standalone component editor checks exact candidates on draft or revision changes, not on every frame. Create may open an existing match; private Copy & Edit may explicitly reassign to one. Save in shared or duplicate mode preserves the independent identity. Unverified Skills profession context cannot authorize automatic reuse.

Nexus options' Public reference catalogs section offers Refresh profession metadata through the standard action control, with a compact cached/refreshing/failed count. It explicitly refreshes all nine professions; ordinary editor demand requests only the relevant profession. Cached selectors and pure getters do not perform SQL or HTTP; missing native editor metadata can use the same manual owner.

Nexus options include Storage & Cache with an explicit Inspect Storage action, explanatory hover tooltip and cached diagnostic snapshot. Use shared section and action controls. No filesystem/SQL scan on each ImGui frame. The Rebuild button sits beside the operation dropdown (wraps at narrow widths) and offers confirmed startup-only rebuild of the entire cache, downloaded artwork, characters, account progress, achievement catalog, shared public catalogs/prices, or inventory/wallet/guild bank. Show operation results and quarantine location; never invalidate live snapshots.

### Multi-select skin filters and split panels
- `UI::MultiFilterChoice` uses an unrestricted empty set and checkboxes; shared `SkinFilters` implements multi-select OR within facets and AND across applicable facets. Browser and Shopping keep independent selections, use removable chips and the same eligibility/count helpers. Browser progress describes selected scope before search/ownership filters; match/shown counts are separate. Catalog and ownership generations invalidate cached projections. Facet menu counts represent whole catalog facets, not conditional intersections. View as Grid is a Skinventory tab menu action, not a filter. Navigation reveals a requested skin by clearing conflicting restrictions. Legacy mandatory category defaults are not migrated into active filters.
- `UI::SplitPanel` captures available dimensions before the left child; use `split.left` for the child and `split.Divider(id, preferred)` between children (owns both SameLine calls). Persist preferred width only on drag release or double-click reset; temporary window clamps do not overwrite preference. Separate settings for Characters, Loadouts, Fashion, Components, Equipment Sets and Skinventory; Achievements retains its existing state file. Keep Nexus ImGui 1.80 ABI.

- All filter popup fields use left-aligned labels and uniform control width through `UI::FilterFieldLabel`, `FilterChoice`, `MultiFilterChoice`, and `FilterInt`; reset is always visible and inert/dim when no active filter chips exist. Loadouts game-mode selection is multi-select OR, with independent removable chips and session migration from the old single integer. Preserve search text on reset.

### Save to Library and Equipment Sets
Character identity appears first, followed by Save as, the component type when relevant, Name (or Replace for an existing component), modes for Complete Loadout, and only the required source tab selectors. Complete Loadout always includes equipment. Equipment-only captures require no build tab. Manual names survive source and target changes. New component can capture Equipment Set, which opens the separate Equipment Sets Library collection; each set can include any nonempty subset of equipment categories, selected at capture. The Loadout component preview groups Base Build and Skills under Build, followed by Equipment Set and individual equipment categories under Equipment, then Fashion. This is visual only. Read-only Loadout and Equipment Set references (including inherited references in the standalone reference draft) share UI::ReferencePreviewRow: measure wrapped category/value text, vertically center both and the link glyph, and use a single full-table-width native selectable for hover/click/context actions. Missing values use the same geometry without an action target; editable combo labels retain frame padding. Top-level Loadout Edit exposes inline reference selection in the parent draft; inherited category choices retain set ownership, and other references, set choice and Fashion can be staged until Save/Cancel. Cross-context and standalone set actions use the shared reference editor. Detach Set is a staged reference operation, not an immediate commit. Open Set, Create Separate Set, and Save as Equipment Set remain explicit actions. Equipment Sets has a read-only membership preview, Edit with a complete name/membership draft, referencing Loadout names, duplicate and unused-only deletion. The aggregate gear preview is read-only outside Edit; linked gear can be edited in the parent draft with private-by-default review or explicit shared consent. Not included preserves the effective component on every linked Loadout. Adding an omitted category to a used set requires confirmation. Complete Loadout capture offers independent components, exact matching set or a new named set. Shared component edits and duplicate consolidation account for set references. No refresh or SQL on naming or browsing.

Library collections retain selection by persistent ID through filters and reordering; an excluded selection keeps its preview and a filter notice. Equipment Sets uses its own persisted SplitPanel width. Detail identity/actions remain outside the scroll child, and action rows use SameLineIfActionFits rather than fixed-width positioning. Confirmation targets carry their original ID and revision or exact Fashion baseline. Existing domain reference checks and editor transaction boundaries are retained.

Fashion is a Save as target in the shared Save to Library dialog: Character, Save as, Name, Equipment tab, Save/Cancel. No build tab, component type or game modes. The general character Save button defaults to the active equipment tab; right-clicking an equipment tab preselects that tab. Live Fashion uses the existing wardrobe capture and native Fashion library, retains source tab/character and partial-capture metadata, and offers Select Existing or Save Separate Copy on an exact wardrobe match. Notes and weight remain editable in the Fashion collection. Do not reintroduce a separate Save Active Fashion button or context action.

### Navigation history

Characters and manual Compare targets use stable account-qualified identity; unresolved manual Compare remains selected with an unavailable message and explicit selector, instead of silently substituting a different character. Capture confirmations become unavailable if the original address changes; cancel and reopen to capture the new verified address.

The main window has shared Back/Forward controls, mouse side buttons and Alt+Left/Right. History is session-only, bounded to 64 entries, and stores stable record IDs. Loadouts and Fashion use record IDs; Characters use native account GUID plus name. Resolve transient indices against the current snapshot. `MarkNavigation()` identifies deliberate selection/cross-reference actions; filters and refreshes update context without pushing an entry. Keep new page destinations in `NavigationUI.h`; use the common history and never add a page-specific stack. Input callbacks queue directions only, respect focus/hover and modal/editor guards, and deregister on unload. Restore existing context, separate Browser/Shopping filters and scroll where available; missing IDs fall back to normal page selection. Character sort mode/direction and custom ordering are global preferences; history never restores an earlier ordering. Restore stable destinations, search, contextual filters and scroll, using the current global ordering. Inline Loadout editing retains ownership of its current collection/record. Modeless editors retain their draft while visible or when the main window is hidden; unrelated editor launches and backup/restore cannot replace active drafts. No history persistence or cache refresh policy changes.

### Editor transaction convention

Read-only previews never mutate saved records. `UI::SaveCancel` delegates to `UI::ActionFooter` (also used by `UI::ConfirmCancel` for destructive confirmations). Caller-owned validation, exact dirty state and pending status govern primary/secondary actions; disabled reasons are available on hover, errors are inline, actions wrap at narrow widths. Auto-resizing destructive confirmation modals use `BeginConfirmationModal` to reserve the measured width of both footer actions (bounded by display width); Delete and Cancel remain adjacent on ordinary screens. Loadouts, Components, Equipment Sets, Fashion (including Delete & Detach), consolidation, account unlink, shared component replacement, cache maintenance and dirty-discard dialogs use this helper. Fast Load is intentionally unchanged; backup import uses its existing explicitly sized editor and shared footer. `EditorLifecycle` and `UI::DiscardRequested` enforce clean close versus explicit dirty discard. Cancel, editor close button and native focused Escape where delivered follow the same draft-close policy. Do not intercept host keyboard events or replace Nexus close-on-Escape; active fields/deeper native popups retain priority. A rejected commit keeps the draft and its stable identity; stale revision or baseline prevents overwriting newer data. Reference drafts (`RenderReferenceEditor`) commit all assignments together in one native transaction. New/Edit Equipment Set and cross-context Loadout reference editors use `UI::ContentSizedModal` for stable display-bounded width and content-driven height; warnings, linked-owner consent and footer are ordinary flow content, not fixed-height hidden reserves. The modal scrolls as needed on shorter displays. Set membership additions require explicit confirmation of replacement on linked Loadouts; removal transfers the original reference. Cross-library Assign/Apply actions open the same Loadout reference draft. Existing typed component and aggregate Loadout payload editors remain separate so selecting a different component cannot accidentally overwrite its stored payload. No new schema or migration. Keep search, sort, and view controls immediate (not persisted record edits).

Fashion and Save to Library modeless editors retain an existing draft instead of replacing it when another record or capture is opened. Opening the same source focuses the existing window; a different source requires finishing the current draft. Component/reference modals also refuse conflicting launches. Backup import blocks while a Library draft is open, including clean provisional drafts and Fashion edits. Existing-look edits use stable ID and exact persisted baseline checks in the repository. The Save/Cancel footer accepts a distinct Save Separate Copy label when an exact Fashion capture match is offered. Aggregate Loadout list selection and drag/reorder are disabled while its draft is active.

The nested gear customization window uses a private equipment draft. Apply stages only equipment fields in the parent Loadout draft; Cancel/close confirms discard when modified, including offhand removal, bulk gear changes and infusion totals. The parent Save stays unavailable until the child is closed; parent Cancel reviews both drafts and must never close the child before confirmation. Keep editing preserves both drafts. A provisional new Loadout is removed only after a successful revision-checked discard; failure retains the draft. Gear edits must not overwrite unrelated Build or metadata fields.

## Character location and loading

The character-row hover tooltip displays the live roster location only; use a map ID fallback if its name is unavailable. Do not add location to the context menu or change API-derived character labels. Right-click Load Character resolves the actual row identity and uses the shared UI admission and deferred execution path described under [Fast Load actions](#fast-load-actions). Disable for active/foreign characters, invalid roster, unsupported resolver or a pending request and explain the reason on hover. The click performs fresh gameplay and context validation; do not disable the menu solely on a periodically sampled gameplay flag. Use the existing Nexus alert for validation failures and outcomes.

### Native inventory

Item-only facets exclude currencies; freshness and quantity apply normally (coin quantity in copper). Visible Items demand can use the existing independent Wallet refresh policy; local filtering never issues requests. The dedicated Wallet retains its pin/zero/game-order behavior. Item filters and local sort are independent from refresh; automatic refresh is opt-in and visible-scope only. Multi-account controls are hidden with one linked account. Shared guild stock is separate from personal totals. Compare's exact saved item locations are informational, not semantic differences. Personal Inventory locations, Compare availability and equipment location menus use NativeInventory::LocationLabel and the numerically sorted cached per-item index. Show one-based Bank tab/slot (30 slots per tab), character bag/slot and shared inventory slot; keep separate physical stacks, existing account prefixes, binding and stale indicators. Invalid positions retain the broad storage label. Materials, Armory, equipment and delivery keep their existing semantics; no guessed guild or material positions. Equipment/Shopping/Compare Find in Inventory actions use a shared navigation target and never fetch on click. Shopping Stock rows have zero remaining purchase cost and link to the corresponding cached item; stale/failed or uncertain acquisitions do not reduce totals.

Inventory subview chips distinguish the selected view. Wallet pins are stored in settings (not cache), pin currency IDs across accounts, and support pinned-only and hide-zero filters; pinned-first game order is fixed. Item filters include character, freshness, aggregate minimum quantity and potential transfer (known public flags, fresh unbound personal loose locations; not a verified trading-post listing). Compare adds exact-ID upgrade and infusion acquisition hints without changing semantic match results.

- Native Inventory Items and Wallet must use `UI::SearchToolbar` with removable chips and canonical `UI::FilterChoice` / `UI::FilterInt` fields; never implement per-view filter combos or a separate row of filter checkboxes. Wallet favorites-only and nonzero balances are filters, not persistent favorite mutations. Guild bank uses `UI::SearchField` while it has no additional facets. Keep sorting and account scope separate from filter reset. The current storage facet remains single-select because it also determines the explicit manual refresh scope; changing search, filters or sorting alone performs no API request.

### Native Inventory UI consistency
Inventory uses the global account selector (empty = All Accounts for multiple linked accounts), the existing tab-dropdown interaction for Items/Wallet/Guild Bank, and a reserved scrollable child plus RefreshUI::Row footer. The shared multi-scope footer reports All scopes current when the typed aggregate is Ready with complete retrieval coverage; otherwise it identifies oldest retained age, incomplete coverage or missing retrieval. Hover shows both most recent and oldest retained retrieval, independent of batch completion. Grouped Bags and Equipment include oldest retained age; missing scopes leave complete coverage unverified and failures retain previous timestamps. Items use multi-select OR within binding/rarity/type/character facets and AND across facets, with individual removable chips; storage remains single-select to preserve manual scope. NavigationUI captures Inventory subview, target ID, search, facets and sort. Reveal uses existing global account scope if the item is there, otherwise All Accounts if a different linked account has cached stock. Wallet and guild coin display reuse RenderCoins; Items/Guild use shared rarity palette and item context menu. Stock Shopping rows retain normal coin-height geometry and locate stock through RenderSkinContextMenu. Native account key fields use canonical InputText with password mask; unlink uses destructive button role and pending actions are disabled. Preserve source/refresh semantics; visual tests outstanding.

The global account dropdown occupies the navigation header (right aligned, wraps when needed), never overlays the primary tab strip. Account validation uses the shared typed refresh status presentation. Location names are shared across item browsing, Compare and equipment menus. The existing equipped-item chat-link action retains instance-specific skin/socket metadata.

Inventory refresh tooltips show the active storage request and processed scope count, with Bags and Equipment grouped by account instead of one line per character. Completed scope status is published immediately through a transient progress overlay; full inventory projections are coalesced on the worker and published after roster discovery and completion. Character and Compare footers use the existing fetch detail for current character ordinal and retrieval stage. No additional API requests or render-time SQL.

Inventory has no inline Storage status tree; the shared footer tooltip owns retrieval diagnostics. Account scope remains in the global header (hidden for a single linked account). Character is the first filter and first chip group. Its multi-select picker shares the profession-colored icon row and cached character ordering with Compare, stays open for multiple choices, and preserves roster-only names with unknown profession. Empty selection means All. The shared picker uses embedded class artwork, never requests profession metadata merely to draw a row. Compare retains its single-target/Active semantics.

Inventory Items List mode is a search-first view when unfiltered: do not scan or render matches until at least three non-whitespace query characters are entered or any meaningful facet is active. Character, storage (including Bags and Wallet), binding, rarity, type, freshness, minimum positive quantity and transferability each enable browsing independently. Multiple character selections count as one facet; global account context and sort do not count. With qualifying filters, empty or shorter queries show all filtered matches (short text is not applied until the minimum is reached). Explicit Find in Inventory navigation can reveal a short numeric ID. Filters remain editable before searching; clearing the query preserves filters and hides results unless the filter-only browse rule is satisfied. Use the existing shared SkinSearchCore token matcher (case-insensitive AND substring tokens, conservative typo tolerance for longer words, literal numeric tokens); tokenize once per query. Other browse-first lists retain their current empty-query behavior. Use HasMinimumQuery for future search-first views rather than embedding a minimum in the input widget itself.

Visible selected equipment, Tools, Loadouts, standalone components and Inventory detail share the item definition owner and seven-day freshness policy; no tooltip-hover or local filter-triggered metadata requests. `RenderItemDefinitionDetails` / `RenderItemDefinitionTooltip` use `TooltipCore::ItemDefinitionLines` for definition type, defense/strength, fixed attributes, upgrade effects and description across these views and Compare. The caller chooses definition sections so actual equipped stats and saved stat intent are not replaced by public fixed attributes. Legendary relic effects are not inferred. Dynamic icons with a known URL use `IconManager::GetOrRequestIcon` (including catalog row/tile, trait, skill, equipment, Fashion and Library); the same URL-qualified cache/worker and failure state apply to all. URL-less fixed/embedded callers can use `GetIcon`. Inventory rows prefer an already-published public icon URL over an older storage projection without fetching definitions from list rendering. The same renderer shows known item level, API vendor value in copper and restrictions from the canonical public definition, never inferring sellability, market value or character eligibility from them.
