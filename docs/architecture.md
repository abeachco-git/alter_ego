# Alter Ego architecture

This is the living architecture reference for the independent experimental branch, not a rollout plan. See [AGENTS.md](../AGENTS.md) for development rules, [UI components](ui-components.md) for presentation conventions, and [regression testing](regression-testing.md) for validation.

## Runtime and integration

Alter Ego is a Windows x64 UCRT DLL loaded by Raidcore Nexus. Nexus supplies the ImGui 1.80 context and allocator; preserve the ABI. The entry point and shared UI state live in `src/dllmain.cpp`, with dedicated composable, fashion, backup, refresh, and presentation helpers. `src/AddonShared.h` exposes shared UI utilities and the Nexus API handle.

`src/GW2API.h/.cpp` manages character data, retrieved build and equipment tabs, accounts, caches and library integration. Character snapshots use native authenticated ArenaNet requests through `NativeAccounts` and `ArenaNetTransport`. Public GW2 catalog GETs use the same transport via `HttpClient`. MumbleLink provides identity and specialization observations, not live equipment contents.

**Threading:** Nexus `Events_Raise()` dispatches synchronously on the calling thread. Never hold a mutex across a query event that can invoke its response handler. Font request callbacks can likewise re-enter synchronously: release the font manager mutex before registration calls and accept updated font pointers when the Nexus atlas is rebuilt.

### Native character loading and location

`GameMemory.h` owns bounded, copied game-roster snapshots and the explicitly
user-initiated character switch. The standalone diagnostic tab was removed
after a successful live roster and off-main-thread switch test. This is an
undocumented, version-sensitive integration, not a supported Nexus contract.
The switch is gated to the inspected structural layout, matching signatures,
complete switch and request function fingerprints, valid context/gameplay and
fresh roster. The November 17 and November 24, 2026 executables match these
checks despite different PE timestamps; timestamps alone are not a gate.
Unrecognized layouts or changed function bodies fail closed. A request remains pending until the
target identity is observed or a 60-second gameplay timeout expires. No
automatic retry, game patch or thread injection. Memory metadata is validated
for plausible ranges and unique names, never required to equal stale API
metadata. The current live roster and any known account conflict govern
eligibility. Map IDs are resolved from public API data in owned worker batches
with session caching; only the row tooltip presents location. Neither map
lookup nor hover performs synchronous HTTP or SQL. On an unsupported game
build, loading fails closed; roster location availability is independent.
The Nexus Fast Load preference controls UI admission only (Disabled, Enabled,
Enabled with confirmation); missing settings preserve Enabled. Characters,
Inventory and Compare use the same existing page-visible Tick and deferred
Process handlers. Confirmation is scoped to the active identity, verified
account and browsing account; cancellation never submits a native request.
Disabled hides load actions but intentionally retains native roster sampling and
location retrieval. Native signatures, scanning cadence, structural validation,
thread ownership, switch invocation and pending-outcome handling are protected:
no refactor or lifecycle change without specific approval. Future character
context menus must follow the [Fast Load action policy](ui-components.md#fast-load-actions)
and reuse the existing admission and deferred handlers; a new page that needs
additional native integration requires separate review.

## Development safety and ownership

These are review rules for changes, not a claim that every existing path has already been audited.

- Keep Nexus/ImGui calls on their documented owning thread. Inspect callback and worker ownership before changing asynchronous code; callbacks must not access destroyed state or publish stale results to a different character/account. Preserve the established shutdown ordering, unsubscribe/release registrations and stop or join owned workers before unloading their code or state. Avoid holding locks while calling re-entrant external APIs.
- Treat refresh policy, cache ownership, invalidation and in-flight deduplication as domain responsibilities. Reuse existing requests and cached snapshots; ordinary drawing, sorting, searching and filtering must not initiate new requests. Preserve approved explicit, scheduled and lazy fetch paths rather than accidentally disabling legitimate lazy loads. Do not alter refresh lifecycles without specific approval.
- Distinguish absent, incomplete, stale and verified data. Failed or partial requests must not silently replace good snapshots or be presented as complete. Use stable identifiers rather than display labels for stored identity and completion matching.
- Keep domain operations independent from presentation when practical. Reuse existing owners for persistence, refresh, catalog matching and comparison. For new substantial functionality, prefer a cohesive module with pure testable helpers where appropriate; avoid mechanical file splitting or a broad rewrite of dllmain.cpp. Do not change unrelated architecture merely to follow this preference.
- Prefer scoped diagnostics with enough context to investigate failures without exposing API keys or private account data. Remove temporary debugging scaffolding after diagnosis, while retaining actionable error handling.

## Vocabulary and components

A Loadout is an ordered composition of reusable component records, with an optional Fashion ID referencing the existing Fashion library.

Ten component categories:

| Component | Fields | Semantic comparison |
| --- | --- | --- |
| base_build | Profession, traits, specialization, pets, legends, Build Template weapon picks | GW2 Build Template meaning |
| skills | Heal, three utility slots, elite, aquatic skills | Utilities are unordered for matching but slot order is preserved for export |
| weapons | Physical weapon sets, weapon type, item ID, stats | Compare by weapon set |
| armor | Armor slots, stats, item IDs | Compare base stats by slot |
| trinkets | Rings, amulet, backpack, accessories and unknown future slots | Compare base stats by slot |
| runes | Global rune, per-slot runes and IDs | Aggregate counts of effects, not placement |
| sigils | Physical sigil data from weapon slots | Aggregate per active weapon set, not per hand |
| infusions | Mutually exclusive slot requirements or aggregate AR/stat targets (legacy conflicts preserved) | Slot requirements or numerical aggregate minimums, according to mode |
| relic | Relic identity and effect | Independent relic comparison |
| aquatic | Optional underwater headgear and weapon slots, including their stats, runes, sigils and infusions | Existing equipment comparison rules; no inferred data |

Equipment remains a logical *view* of its components, never a second monolithic saved object. Build is the combination of base_build and skills. Named Equipment Sets own any nonempty subset of eight equipment categories. A linked Loadout stores one set ID and direct references for every category not included in the set, plus Base Build and Skills. A category has exactly one owner when present. Removing membership transfers its existing reference to each linked Loadout; adding membership replaces direct references after confirmation. EffectiveRefs is the canonical expansion used by Resolve and projection invalidation. Set membership edits propagate to linked Loadouts. Detach transfers existing references without duplicating payloads; Copy & Edit Set creates a separate named set with the same component references. Shared component payload edits still propagate to their owners. A referenced set cannot be deleted.

Infusion mode is inferred from the existing typed payload, including effective Aquatic references; no schema change is necessary. Slot mode derives read-only totals separately for each terrestrial and aquatic weapon configuration. Aggregate targets refer to terrestrial configurations, and no unknown bonuses are inferred. Mixed legacy records remain lossless and require explicit resolution; new conflicting shared/reference changes on existing owners are rejected. Alternate modes are temporary editor drafts, never parallel authoritative saved requirements.

## Storage invariants and native repository

- Durable library: `library/library.db`, native SQLite schema version 5. Existing v4 is backed up and rebuilt atomically, preserving effective Loadout projections, terrestrial IDs and unused aquatic fragments; archive experimental SQLite versions 1–3 before migrating the original v2 library. Foreign keys and triggers prevent mixed direct/linked equipment ownership. No monolithic disk mirror.
- Ten independent categories, stable category-scoped IDs and ordered loadouts with optional Fashion foreign keys.
- Typed relational rows store known fields. Child tables retain physical equipment slots, utility and infusion ordering, exact IDs, mode associations, skins and dyes. Nullable columns and presence flags distinguish absent and empty; JSON extensions preserve unknown external fields.
- Nonunique indexed fingerprints shortlist exact candidates. Verify complete normalized content before reuse; functional Compare rules are not storage identity.
- Ordinary edits reuse matching components, update unshared records, and copy shared records privately. Explicit shared edits and deliberate independent copies remain available. Never automatically remove unused components.
- `SavedBuild` is a transient presentation/editor projection, not authoritative saved data. Cancel never commits a draft; unaffected resolved records can be reused after commands.

`Database.h` provides owning RAII connections, prepared statements, bound values, rollback transactions, application identity and schema versioning, integrity/foreign-key checks and online backup. Durable connections use DELETE journaling, FULL sync and a bounded 1.5-second busy timeout. One connection and its statements belong to one thread; never invoke external callbacks while a transaction is open.

`NativeLibrary.cpp`, `NativeLibrarySchema.h`, and `NativeLibraryCodec.h` own relational queries and conversions. Repository writes are atomic, revision-checked and limited to changed records. `NativeLibraryStore` serializes commands and publishes committed snapshots; no SQL belongs in rendering. `NativeLibraryEditing.h` provides field-level draft overlays, exact candidate indexing, shared-use checks and private edits. `ComposableSemantics.h` remains the separate functional Compare engine.

Startup stages and verifies migration of legacy build and Fashion files, reopens the candidate database, archives byte-verified originals under `backups/migration/`, then publishes without replacing an existing database. Existing initialized databases always win, even when empty; corrupt or foreign databases fail closed. Archive/remove experimental v3 files before migrating a pre-composable library. Do not migrate the v3 graph or maintain reverse synchronization.

`NativeLibraryPortable.h` and `LibraryBackup.h` export versioned portable JSON and ZIP archives; complete graphs include unused components and linked Fashion dependencies. Legacy monolithic JSON remains an import boundary only. Pre-release compatibility scope: preserve existing local SQLite data with backed-up migrations, supported original Pie or Cake import/export and GW2 build links, current Alter Ego portable round-trips, and Snow Crows/MetaBattle runtime imports and refresh. Current portable Component, Loadout, Equipment Set and library packets require first-class Aquatic ownership; obsolete packets with aquatic slots split across terrestrial components are rejected rather than normalized. The v4-to-v5 local SQLite migration still invokes `NormalizeAquatic` independently. Do not confuse portable interchange with local database migration/recovery; retain valid unknown extension fields within supported formats. Restore previews selections, protects references, creates a recovery ZIP and a verified native online backup under `backups/recovery/`, then commits changes. Keep full database backup/recovery distinct from portable interchange; the native copy is for recovery and the ZIP is selective.

### Storage paths and cache ownership

`StoragePaths.h` defines the shared directory layout. The four settings/session/UI JSON files live in `config/`; pinned achievement state and login timestamps live in `library/`. Existing destination files win. Valid root-level JSON is byte-verified, archived under `backups/migration/`, staged, then published without replacing a destination. Failed or malformed migrations retain the original path. Portable ZIP entry names remain unchanged for compatibility; backup reads and restore writes resolve the same canonical paths.

`cache/cache.db` uses independent application identity and schema versioning. The achievement progress repository owns typed account snapshots, progress records and completed bit rows. Full account names are keys; legacy slug files are imported only when their embedded identity matches. Transactions replace one account at a time, reject older fetch timestamps and retain the previous committed snapshot on failure. SQL runs at existing persistence boundaries, not on every render frame. Connections are short-lived and serialized; current journal settings remain DELETE/FULL pending concurrency measurements. A corrupt or foreign cache is reported rather than silently overwritten; close the addon before deleting the rebuildable cache DB.

Cache schema v2 also stores achievement definitions, ordered bits/flags/prerequisites, groups, categories and ordered membership, search names (obsolete hero challenge metadata removed in v14 and waypoint mappings in v15). Reference freshness is dataset-scoped. The established UI projections are reconstructed in bulk; JSON is a transient codec and legacy import boundary only. Cache schema v3 adds shared skin metadata, subtype/weight, restrictions, flags, ordered dye materials and exact-account ownership snapshots. Fashion and Skinventory keep separate in-memory projections and completeness markers but write the same authoritative relational skin records; narrower responses cannot remove the other projection's fields. Legacy skin and ownership files are read only at migration. Cache schema v4 stores the Skinventory item map, many-to-many candidate relationships, vendor costs, normalized item price observations and per-skin verified cheapest-choice references. Failed refreshes preserve previous prices; TTL still governs retries. Schema v27 adds the canonical latest item-ID observation cache, seeded from prior winners. Inventory and Skinventory use the same RefreshEngine ID claims, HTTP transport, one-hour TTL and failure cooldown; skin choices derive from complete candidate coverage (oldest candidate timestamp), with legacy choices retained only as fallback. Item prices survive mapping changes and are cleared by public catalog maintenance. Other public reference/account snapshots remain JSON under `cache/`, with textures and wiki images moved to `cache/textures/` and `cache/wiki_images/`. Legacy rebuildable files move only when a canonical destination is absent. Further relational public metadata migration and cache diagnostics remain outstanding. User pins, preferences, manual progress and saved library records must survive cache deletion. Keep textures, fonts and portraits as ordinary files; do not store large JSON documents as opaque SQLite payloads. Vendored SQLite update procedure: [lib/sqlite/README.md](../lib/sqlite/README.md).

## Presentation and resources

No separate font is bundled or downloaded by the addon. Custom fonts use the Nexus file registration API. The default font path leaves the ambient Nexus font unchanged; saved legacy face 1 (Inter) falls back to Nexus, while face 2 remains custom. Preserve exact stored fields when presenting or editing incomplete imported data; Cancel must not persist edits.

Fixed profession, specialization, crafting and status icons are version-controlled in `assets/icons/` and embedded offline during compilation. The manifest records provenance and hashes; CI checks linked resource bytes. Update artwork only through explicit reviewed maintenance. Item, skin, skill and companion artwork uses a persistent runtime cache. Do not reintroduce removed raid/strike banner artwork unless explicitly requested.

Achievement names and definitions are retrieved directly from ArenaNet. The legacy single-achievement waypoint catalog is retired; no externally hosted achievement dataset is required.

AE2 interchange is separate from the internal native data model: see [shared build specification](shared-build-spec.md) and the vendored JavaScript reference implementation in `lib/alter-ego-build/`.

## Release precautions

Keep the experimental branch separate from main until explicitly approved. Before merging, validate real-library migration, restart, component editing and comparison, imports, Fashion, ZIP restore and normal in-game behavior. CI compilation and unit tests do not replace in-game validation.

### Explicit component consolidation

The Components detail pane offers exact duplicate consolidation into the selected survivor, with affected Loadout names and confirmation. The native transaction revalidates equality, revision and skill profession compatibility before rewriting references and deleting the redundant record. Independent duplicates remain valid until explicitly consolidated. Usage counts are indexed per library revision; existing editor drafts reject a changed library revision rather than overwriting newly saved data.

Private Copy & Edit offers explicit reuse of an exact compatible component, verified again in the native transaction against the current revision and original reference. Shared edits and intentional duplicates preserve their identity; exact matches are disclosed rather than silently consolidated. Private Base Build editing cannot change the profession of an already referenced Loadout.

Cache schema v5 stores specializations, ordered minor/major trait IDs, traits, skills, ordered profession membership, item stats and ordered attribute names, and dyes with native RGB channels for each material. Only the API's heterogeneous tooltip facts remain per-record JSON. ReferenceMetadataCache owns atomic snapshot replacement, stale-capture rejection, native-first legacy migration and bulk projections; no network policy changes. Item metadata, item names, character/Vault/Clears snapshots and wiki data remain to be evaluated separately.

Cache schema v6 consolidates item details and Commerce item names in reference_items; the complete flag distinguishes a public detail fetch from a name-only record. Commerce owns candidate membership and pricing, not a second name table. Exact name-to-ID aliases remain a separate relational lookup to preserve selected IDs for ambiguous names and historical spellings. Full details take precedence over narrower Commerce names. Type-specific item details remain an API extension field; typed common metadata is authoritative. Item/name JSON is legacy migration input only. SaveItemNameCache clears its dirty flag only after a successful commit of the same in-memory snapshot.

Storage & Cache diagnostics are available in Nexus addon options on explicit inspection. A read-only SQLite connection checks identity, schema, quick integrity and foreign keys, and reports database sizes, reference counts and freshness plus downloaded artwork size. Diagnostics do not create, migrate, repair, delete, or fetch anything. All-cache rebuilding remains a game-closed operation; selective live invalidation requires coordination with in-memory projections and workers.

Native graph merges reuse a colliding ID only when both name and exact payload match; Skills additionally require independently verified matching professions. Conflicts are remapped without consuming another incoming component's original ID. Unused independent components remain intact.

Inherited category reference replacements use the parent draft and the same reference picker/rebase machinery. The staged replacement map is never persisted as a competing direct reference. The existing parent Save review separates shared reference replacement (changes only set membership, not either component payload) from shared payload editing. Private changes fork a shared set once, single-owner changes reuse the set, and explicit shared choices affect its linked owners. Other categories remain intact. Conflicting unsaved content edits require saving or undoing that category before replacement; a staged replacement must be saved before editing that category's payload. Exact selected IDs, including equivalent independent copies, are preserved.

Library schema v7 adds typed component name provenance (unknown, manual, automatic, automatic pending). Existing v6 names migrate to unknown after the normal verified backup. Provenance is separate from payload identity, fingerprints and Compare semantics and round-trips through native component, Loadout and library interchange. Deliberate naming uses the shared suggestion helper; manually named copies and imported unknown names are protected. Automatic names update on deliberate payload edits. Deferred metadata repair only resolves explicitly pending automatic names when all required cached metadata is available, with no HTTP or repeated renaming of complete names. Run at startup after cached metadata loads and as part of existing successful explicit library transactions, not as a new render-time or concurrent database task. Unique names exclude the current ID; exact reuse retains the existing record's provenance.

Aggregate Loadout edits enforce the same profession guard as private and shared Base Build edits: create a new Loadout to change profession. Legacy migration never deduplicates Skills with missing profession context, even if their payload is identical.

Cache schema v7 moves the character projection to typed character, crafting, equipment, ordered upgrade/infusion/dye, attribute, tab-name, build/skill/spec/pet/legend/weapon records (obsolete hero-point records removed in v14). Exact account and character identities distinguish unknown-account legacy rows. Native presence wins over legacy JSON, including empty snapshots. Capture and write are serialized; a full projection is replaced atomically at the existing persistence boundary. Current incremental character writes and verified roster reconciliation are described below. Newly supported pet, legend, weapon and binding fields retain missing-field markers rather than inventing known data. No refresh policy change.

Cache schema v8 replaces sanitized Clears and Wizard's Vault filenames with independently keyed exact-account snapshots, typed section/entry/bit and period/objective rows, and season metadata. Existing reset filtering and request scheduling remain in Clears.cpp. Persist original legacy snapshots before reset filtering; require an embedded matching identity for scoped legacy files and verified single-account context for old unscoped input. Writes are serialized and transactional; older dataset timestamps are rejected. Runtime cache loading rechecks the represented account before publishing. Diagnostics includes both datasets. Current section freshness and generation fencing are described in the objective rollover and account ownership sections below.

### One-shot worker ownership

`BackgroundWorkers.h` owns the joinable one-shot jobs previously detached in GW2API, Clears, Skinventory, Commerce, achievement metadata, relay and website imports. Completed handles are reaped on launch. The lifecycle owner opens the registry during load, closes admission before deregistering callbacks and joins all jobs before persistence and subsystem teardown. Domain busy-state failure handlers run outside the registry lock; cancellation is cooperative and exceptions do not escape the worker entry point. Large aggregate fetches check cancellation at batch boundaries. WinINet read helpers reject truncated responses and use the existing 12-second operation timeout across clients. This is not a hard total network deadline; DNS/proxy resolution and synchronous external callbacks still require runtime validation. Icon and WikiImage retain their existing owned queue workers. Font release is outside the font mutex; callback deregistration semantics and full account-generation validation remain outstanding. No request scheduling, retry cadence or startup policy changes.

Only explicit verified account rosters authorize pruning. Registry-only fast paths no longer authorize deletion. Character reads use immutable revision-cached shared projections; account and pending-list reads return copies. Critical partial or malformed replies do not replace the previous character. Exact account and character identity governs replacement and crafting reuse. No refresh cadence or schema change.

Completed character refreshes serialize only the exact account/name record once a native snapshot exists. Incremental SQL replaces that character and its children in one transaction, retaining its row ID and order, rejecting older per-character freshness and leaving other records intact. Only the first snapshot retains the aggregate transaction. Verified roster deletion uses a targeted account-scoped transaction, commits before publishing the removal, and retains previous rows on failure. A failed baseline inspection fails closed. No schema version change.

### Startup cache maintenance

The Storage & Cache options schedule an exclusive, fixed-operation request under `config/cache-maintenance-request`. On next startup, before subsystem initialization or background jobs, `CacheMaintenance.h` consumes the request and either quarantines the entire cache directory (including damaged DB and sidecars), archives artwork and failure markers while retaining wiki acquisition metadata, or invalidates one relational dataset group in a transaction after archiving known legacy sources. Public catalogs and Commerce share item identity and are invalidated together. Account progress includes Clears, Vault, owned skins and achievement progress; durable pins are separate. Normal fetch paths rebuild data without changing their cadence. Moved files remain under `backups/cache-quarantine`; partial failure is reported rather than silently deleting or retrying against newly rebuilt data. No durable library, configuration, login history or recovery backup is removed. This is restart-only, not live eviction.

The dedicated IconManager and WikiImage queue threads close admission and notify before addon deregistration; all one-shot jobs and both queues are joined before API teardown. Queue exceptions and cancellation release loading markers without treating shutdown as a confirmed remote failure. Worker audit covered all runtime translation units; external callback quiescence is a separate open workstream.

### External callback admission

`CallbackLifetime.h` provides a shared local admission gate for render/options, input, Nexus events (including Skinventory) and font callbacks. Close admission before deregistration, then drain admitted bodies before worker join and state teardown. The gate mutex is never held across callback bodies or host calls, including synchronous reentry. This does not serialize concurrent admitted bodies or prove host deregistration quiescence: Nexus must not call into unmapped DLL code. Close-on-escape is a registered raw pointer, and texture loads with null callback depend on the host's resource ownership. Unload must not be invoked reentrantly from an admitted callback; the host lifecycle contract and in-game behavior remain to be verified.

Cache schema v9 stores wiki acquisition metadata and skin/currency failure timestamps in separate typed tables. WikiMetadataCache owns native-first legacy migration and transactional snapshots with independent presence markers. WikiImage retains in-memory projections; no render-time SQL was added. Startup artwork reset preserves acquisition metadata and empties only negative-cache records, retaining the authoritative empty marker. Existing image bytes remain ordinary files. Skin preview recovery now checks positive cached files before negative records. A one-time reference freshness marker removes old ambiguous skin negatives (not currency failures). Only verified missing discovery uses the seven-day persistent skin cooldown; HTTP/parse/download failures use a 15-minute session cooldown. Exact non-armor filename lookup uses verified imageinfo, falling back to combined page images/categories with existing weight-specific candidates. Cached texture publication has a bounded visible wait; manual Retry bypasses skin cooldowns but not shared admission. Metadata acquisition remains separately scheduled.

`AccountIdentity.h` defines exact account/character identities and a shared reply matcher. Echoed account names must match; old non-echoing responses are accepted only with verified single-account context. Skinventory distinguishes full API and batch ownership requests, verifies endpoint and captured account epoch before publishing, validates complete requested batch ID sets, and keeps partial batch results separate until completion. The opportunistic fashion unlock map is invalidated when the logged-in account changes. Clears, Vault and achievement replies check the represented account under publication mutexes and cap response array access. Further typed selection and completion correlation remain open.

## Native account retrieval

`config/accounts.db` is a durable account registry keyed by ArenaNet GUID. Windows Credential Manager stores keys separately from exportable data. Native character, skin ownership, account achievement, Clears and Vault consumers use the account GUID, owned workers and direct typed results, using native authenticated requests. Character equipment/build tabs are retrieved in bulk; complete successful character snapshots replace only the corresponding identity. Verified same-character legacy rows may be superseded by a fresh GUID record. The Library remains shared and account-independent. Character identity evidence is reconciled by the shared authenticated roster owner before pruning. Account registry schema v7 stores stable bindings and the last successful raw roster observation; cache schema v29 adopts both in one replayable cache transaction. Character details, bags and physical equipment capture binding revisions and reject obsolete publications; activity scope verification resets when ownership changes. Ordinary core responses supply identity evidence; other admitted character requests reuse a matching core proof for up to 30 seconds or retrieve it. Roster discovery expands only for unresolved ownership, explicit full verification or ordinary timed roster demand. Native inventory and roster tables in cache schema 10 are scoped by GUID. The full account achievement response is shared by overlapping consumers and replaces the account progress snapshot; category selection must not repeatedly download it. Daily/weekly Vault rollover validation remains in Clears. Keys are entered explicitly in Nexus options; no external credentials are imported. In-game and independent freshness validation remain required.

Cache schema 11 adds independent wallet balances/currency definitions, guild leader access and globally GUID-keyed guild bank slots/coins, and public item binding flags. Personal loose-stock availability excludes guild, equipped, armory, delivery, stale and failed rows; missing stat selection is not a verified match. Inventory owns an immutable item/location index; Compare's exact-ID acquisition aid does not alter semantic equality. Shopping subtracts only fresh loose items mapped uniquely to one locked skin by the known acquisition catalog. Remaining totals are conditional on actual game eligibility. Wallet and guild views use separate queries; automatic inventory refresh follows the activity-aware, per-scope policies in the Unified freshness engine section below; manual refresh bypasses ordinary freshness and failure cooldown, not permissions or in-flight ownership. No search/filter-triggered requests.

Automatic API refresh has a master opt-in and durable per-dataset inclusion mask in settings.json. Character, achievements, skin ownership, public catalog, Clears, Vault and each inventory storage have independent gates. Manual actions bypass inclusion gates. ArenaNetAdmission provides bounded, cancellation-aware request admission with shared rate limits and priority ordering (see Unified freshness engine). It is not a fully deduplicated dataset scheduler.

Vault cache schema 12 gives each daily, weekly and special section its own confirmed timestamp. Verified responses publish independently; failure, rate limit, reset-held or missing responses preserve the other periods. A transactional merge retains older rollover fingerprints for invalidated sections and rejects late older period writes. Automatic entry/reset/retry checks select stale unclaimed or unverified periods; explicit Refresh still requests all three. The footer uses the common aggregate retrieval coverage label and newest/oldest retained ages. Verified fully claimed sections remain current for their period until reset; overdue unclaimed sections are due. Per-section inspection feeds scheduling and status; do not infer period completion from retrieval age alone. Clears has independent section persistence as described for cache v26 below.

Cache schema 13 adds nullable remaining charges to character equipment; older rows remain unknown, explicit zero survives round-trip. Character-wide gathering/fishing/Jade Bot items from the existing supplemental equipment response are normalized to tab zero, independent of template selection. Existing character item/skin metadata batching includes these rows. No additional authenticated requests or durable library schema changes.

### Achievement definitions and ID discovery

`AchievementDefinitionOwner.h` is the shared public definition owner for the category browser, pinned tracker, name-index scanner and Clears. It reuses `RefreshEngine` per-ID claims, `AchievementCatalogCache` and reference request-start watermarks. Validated complete batches (up to 200 IDs) commit definitions, names and per-ID observation stamps together before publishing immutable payloads; release successful IDs incrementally. Failures retain verified data, and only actual failed transport attempts create the ordinary per-ID cooldown. Cancellation and local admission rejection are not remote failures. Successful per-ID observations are fresh for 30 days, including after restart; legacy definitions without verified stamps remain usable but are eligible for demand-driven revalidation. Visible category and pin checks request missing IDs and, with Public Catalogs automatic refresh enabled, stale IDs. Explicit demand can bypass cooldown; no startup definition sweep.

`AchievementNamesCore.h` validates complete ID lists and plans missing-only or explicit full retrievals. Startup restores names and definitions without HTTP. A first unverified index is checked lazily when Achievements opens; verified ID discovery is eligible after 24 hours with Public Catalogs enabled. Discovery failure backs off five minutes. The existing Refresh Achievement Definitions action explicitly revalidates every listed ID, bypasses freshness/cooldowns and captures the observation baseline once so overlapping successful requests, including those finishing before a later batch, satisfy the scan without duplicate retrieval. Retired IDs remain available for historical/pinned name resolution. `ach_name_index_verified` records only a completed ID check, independent of ordinary definition writes and legacy imports. Achievement-catalog maintenance clears its own watermarks and freshness; general public-catalog maintenance preserves achievement-owned stamps.

Group/category refresh independently validates full snapshots against the public ID lists and checks membership, commits raw snapshots at request-start time before replacing the projection, and reapplies curated event overrides after load/publication. Failed validation or persistence preserves the previous projection. Typed render-owned category demand binds category, account, credential generation, navigation revision, catalog revision and automatic/manual reason. Recheck identity at progress admission; obsolete public requests may complete/cache without triggering obsolete authenticated progress. Visible categories and pinned trackers recover eligible missing/stale definitions without a global category-fetch gate. Account progress scheduling and broker remain unchanged. Clears uses the shared achievement-definition owner and an independent session-only reset-epoch public membership/section cache described below. A generic base definition or achievement category snapshot cannot establish a rotating section's current membership.

The existing Commerce full scan captures upgrades in the same pass. Subsequent equipment refreshes fetch the public ID index, new IDs, and known upgrades in batches, sharing Commerce's in-flight gate. Public Vault definitions are separate from account completion. ### Character summary retrieval and batching

**Principle:** retain the existing freshness engine as the authority for *when* requests originate; batch already-eligible work when doing so reduces requests. Automatic full-character retrieval is independent of the selected subtab. Manual actions retain their explicit scope. Never create an automatic job solely for opportunistic targets.

| Trigger | Retrieval and target selection |
| --- | --- |
| Characters, selected character due | Complete character summary; also consider the active character if due and within the visible account context. |
| Compare, rendered target due | Complete character summary for that target. |
| Existing automatic full request | Fill its first same-account batch with eligible previously retrieved characters, up to 20 total per account. Original selected/active targets precede extras. |
| Manual Characters footer Refresh | Selected character's visible scope mask (core/crafting and the relevant build/equipment/physical scopes). |
| Manual Compare footer Refresh | Selected comparison target's core, build tabs, equipment tabs and physical equipment. |
| Row Refresh Character | One complete character, no opportunistic expansion. |
| Refresh Selected / explicit full refresh | Only explicitly selected/admitted targets, grouped by account and split into batches of at most 20. |
| Refresh Character List | Separate authoritative name roster and identity verification; not a general character-data refresh. |
| Inventory bags/equipment refresh | Targeted character storage request; reuse an overlapping successful summary or targeted observation when available. |

The documented [character summary API](https://wiki.guildwars2.com/wiki/API:2/characters) supports explicit percent-encoded names using `/v2/characters?ids=...` with schema `2024-04-01T00:00:00.000Z`. A single complete character uses the same summary path with one ID. Twenty is an application limit, not a claimed API limit. No accumulation delay, new timer, hidden-window sweep, unrelated account or overflow batch solely for extras. Accounts without the required characters/builds/inventories permissions keep permitted narrow retrieval; do not add opportunistic targets to them.

**Admission and priority.** `GW2API::RequestCharacterActivityRefreshAddresses` collects original exact account-qualified addresses and cached candidates with at least one independently verified detail stamp, matching current roster binding and normalized identity evidence. `CharacterScopes::Due` uses the existing activity tracker, permission mask, logout propagation, specialization, retry and stagger rules; eligibility is not equivalent to elapsed wall-clock cache age. `CharacterBatch::OpportunisticTargets` deduplicates keys, preserves original demand order and fills only available capacity on triggered accounts. Unvisited roster-only characters are not bootstrapped opportunistically. Worker admission rechecks exact binding/credential and eligibility, including the original trigger before entering the shared storage broker. The final broker currently receives addresses without seed roles, waits for its mutex, and can discard invalid originals independently; whether the original trigger remains valid at actual dispatch, and whether skipped extras can reach narrow repair, are open [9B.3](roadmap.md) admission investigations. Selected/active results precede opportunistic character detail projection commits; storage publication uses its own validated owner and does not promise the same per-character order. A full summary may update additional independently validated scopes even when only one scope justified retrieval; their original activity tickets still govern coverage.

**Shared ownership and publication.** `CharacterBatchCore.h` owns bounded named request construction, response indexing, identity evidence and template validation. `GW2API::RequestNativeCharacters` owns character detail admission, independent scope activity tickets and transactional character cache publication. `NativeAccounts::RequestCharacterSummaries` and targeted bags/equipment requests share the storage broker and its serialization, endpoint-shaped session caches and canonical `NativeInventory` parsers. Storage tickets start before transport; successful bags/equipment publish through the same durable owner as Inventory-only requests. Each scope keeps its actual observation timestamp; missing or invalid data cannot make another scope current. A successful bags-only refresh does not advance character detail timestamps. Account credential generation and exact binding revisions fence publication, including failures. No credential lock spans HTTP. Overlapping storage consumers reuse successful observations under the existing owner policy; this is not a guarantee of eliminating every sequential request.

**Failure handling.** Explicit bulk reads accept HTTP 200/206 and validate exact requested names; reject duplicate/unrequested identities, and allow targeted repair for missing rows or invalid fields. Explicit size rejection (413/414) may split the request; unsupported/permission/not-found responses (403/404/501) may fall back to narrow retrieval for original automatic demand, not unrelated opportunistic targets. Transport, rate-limit and server failures retain verified data and apply existing cooldowns rather than fan out into individual requests. Preserve independent scope coverage, partial commits and existing roster recovery. The authoritative name-only roster and independent retirement evidence remain separate. Full roster verification already uses bounded named summary reads for identity evidence and caches matching core proofs; reuse of additional validated payload fields through canonical detail/storage publication remains unresolved (9B.3). Do not take storage ownership under the roster broker or advance freshness from identity evidence alone.

**Item metadata.** Collect known item IDs, upgrades and infusions from committed character/storage results across the job; deduplicate and pass missing complete detail/binding metadata to the existing per-ID ItemMetadata owner, using the shared 200-ID bulk limit. Targeted tooltips/imports and Inventory enrichment retain their existing demand and claim/coalescing behavior. Do not generate extra catalog sweeps, refresh unrelated definitions just to fill capacity, or fetch Trading Post prices merely because character ownership changed. Price TTL remains independent.

Native Fast Load, transport timeout and throttling, ordinary intervals, propagation grace, cache schemas and independent account storage policies are unchanged. Authenticated user testing verified field equivalence for two characters and successful exact coverage through 12 characters; this supports summary retrieval but does not establish 20-character latency or in-game concurrency behavior. See [regression testing](regression-testing.md) and [development status](development-status.md) for remaining acceptance.
