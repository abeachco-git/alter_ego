# Alter Ego architecture

This is the living architecture reference for the independent experimental branch, not a rollout plan. See [AGENTS.md](../AGENTS.md) for development rules, [UI components](ui-components.md) for presentation conventions, and [regression testing](regression-testing.md) for validation.

## Runtime and integration

Alter Ego is a Windows x64 UCRT DLL loaded by Raidcore Nexus. Nexus supplies the ImGui 1.80 context and allocator; preserve the ABI. The entry point and shared UI state live in `src/dllmain.cpp`, with dedicated composable, fashion, backup, refresh, and presentation helpers. `src/AddonShared.h` exposes shared UI utilities and the Nexus API handle.

`src/GW2API.h/.cpp` manages character data, retrieved build and equipment tabs, accounts, caches and library integration. Character snapshots use native authenticated ArenaNet requests through `NativeAccounts` and `ArenaNetTransport`. Public GW2 catalog GETs use the same transport via `HttpClient`. MumbleLink provides identity and specialization observations, not live equipment contents.

**Threading:** Nexus `Events_Raise()` dispatches synchronously on the calling thread. Never hold a mutex across a query event that can invoke its response handler. Font request callbacks can likewise re-enter synchronously: release the font manager mutex before registration calls and accept updated font pointers when the Nexus atlas is rebuilt.

### Native character loading and location

`GameMemory.h` owns bounded, copied game-roster snapshots and the explicitly
user-initiated character switch. The standalone diagnostic tab was removed
after a successful live roster and off-main-thread switch test. This is an
undocumented, version-sensitive integration, not a supported Nexus contract.
The switch is gated to the inspected structural layout, matching signatures,
complete switch and request function fingerprints, valid context/gameplay and
fresh roster. The November 17 and November 24, 2026 executables match these
checks despite different PE timestamps; timestamps alone are not a gate.
Unrecognized layouts or changed function bodies fail closed. A request remains pending until the
target identity is observed or a 60-second gameplay timeout expires. No
automatic retry, game patch or thread injection. Memory metadata is validated
for plausible ranges and unique names, never required to equal stale API
metadata. The current live roster and any known account conflict govern
eligibility. Map IDs are resolved from public API data in owned worker batches
with session caching; only the row tooltip presents location. Neither map
lookup nor hover performs synchronous HTTP or SQL. On an unsupported game
build, loading fails closed; roster location availability is independent.

## Development safety and ownership

These are review rules for changes, not a claim that every existing path has already been audited.

- Keep Nexus/ImGui calls on their documented owning thread. Inspect callback and worker ownership before changing asynchronous code; callbacks must not access destroyed state or publish stale results to a different character/account. Preserve the established shutdown ordering, unsubscribe/release registrations and stop or join owned workers before unloading their code or state. Avoid holding locks while calling re-entrant external APIs.
- Treat refresh policy, cache ownership, invalidation and in-flight deduplication as domain responsibilities. Reuse existing requests and cached snapshots; ordinary drawing, sorting, searching and filtering must not initiate new requests. Preserve approved explicit, scheduled and lazy fetch paths rather than accidentally disabling legitimate lazy loads. Do not alter refresh lifecycles without specific approval.
- Distinguish absent, incomplete, stale and verified data. Failed or partial requests must not silently replace good snapshots or be presented as complete. Use stable identifiers rather than display labels for stored identity and completion matching.
- Keep domain operations independent from presentation when practical. Reuse existing owners for persistence, refresh, catalog matching and comparison. For new substantial functionality, prefer a cohesive module with pure testable helpers where appropriate; avoid mechanical file splitting or a broad rewrite of dllmain.cpp. Do not change unrelated architecture merely to follow this preference.
- Prefer scoped diagnostics with enough context to investigate failures without exposing API keys or private account data. Remove temporary debugging scaffolding after diagnosis, while retaining actionable error handling.

## Vocabulary and components

A Loadout is an ordered composition of reusable component records, with an optional Fashion ID referencing the existing Fashion library.

Nine component categories:

| Component | Fields | Semantic comparison |
| --- | --- | --- |
| base_build | Profession, traits, specialization, pets, legends, Build Template weapon picks | GW2 Build Template meaning |
| skills | Heal, three utility slots, elite, aquatic skills | Utilities are unordered for matching but slot order is preserved for export |
| weapons | Physical weapon sets, weapon type, item ID, stats | Compare by weapon set |
| armor | Armor slots, stats, item IDs | Compare base stats by slot |
| trinkets | Rings, amulet, backpack, accessories and unknown future slots | Compare base stats by slot |
| runes | Global rune, per-slot runes and IDs | Aggregate counts of effects, not placement |
| sigils | Physical sigil data from weapon slots | Aggregate per active weapon set, not per hand |
| infusions | Installed IDs/locations, aggregate requirements, AR/stat totals | Aggregate totals/requirements, not slot |
| relic | Relic identity and effect | Independent relic comparison |

Equipment remains a logical *view* of its components, never a second monolithic saved object. Build is the combination of base_build and skills. Named Equipment Sets own any nonempty subset of seven equipment categories. A linked Loadout stores one set ID and direct references for every category not included in the set, plus Base Build and Skills. A category has exactly one owner when present. Removing membership transfers its existing reference to each linked Loadout; adding membership replaces direct references after confirmation. EffectiveRefs is the canonical expansion used by Resolve and projection invalidation. Set membership edits propagate to linked Loadouts. Detach transfers existing references without duplicating payloads; Copy & Edit Set creates a separate named set with the same component references. Shared component payload edits still propagate to their owners. A referenced set cannot be deleted.

## Storage invariants and native repository

- Durable library: `library/library.db`, native SQLite schema version 4. Fresh schema only; archive experimental SQLite versions 1–3 before migrating the original v2 library. Foreign keys and triggers prevent mixed direct/linked equipment ownership. No monolithic disk mirror.
- Nine independent categories, stable category-scoped IDs and ordered loadouts with optional Fashion foreign keys.
- Typed relational rows store known fields. Child tables retain physical equipment slots, utility and infusion ordering, exact IDs, mode associations, skins and dyes. Nullable columns and presence flags distinguish absent and empty; JSON extensions preserve unknown external fields.
- Nonunique indexed fingerprints shortlist exact candidates. Verify complete normalized content before reuse; functional Compare rules are not storage identity.
- Ordinary edits reuse matching components, update unshared records, and copy shared records privately. Explicit shared edits and deliberate independent copies remain available. Never automatically remove unused components.
- `SavedBuild` is a transient presentation/editor projection, not authoritative saved data. Cancel never commits a draft; unaffected resolved records can be reused after commands.

`Database.h` provides owning RAII connections, prepared statements, bound values, rollback transactions, application identity and schema versioning, integrity/foreign-key checks and online backup. Durable connections use DELETE journaling, FULL sync and a bounded 1.5-second busy timeout. One connection and its statements belong to one thread; never invoke external callbacks while a transaction is open.

`NativeLibrary.cpp`, `NativeLibrarySchema.h`, and `NativeLibraryCodec.h` own relational queries and conversions. Repository writes are atomic, revision-checked and limited to changed records. `NativeLibraryStore` serializes commands and publishes committed snapshots; no SQL belongs in rendering. `NativeLibraryEditing.h` provides field-level draft overlays, exact candidate indexing, shared-use checks and private edits. `ComposableSemantics.h` remains the separate functional Compare engine.

Startup stages and verifies migration of legacy build and Fashion files, reopens the candidate database, archives byte-verified originals under `backups/migration/`, then publishes without replacing an existing database. Existing initialized databases always win, even when empty; corrupt or foreign databases fail closed. Archive/remove experimental v3 files before migrating a pre-composable library. Do not migrate the v3 graph or maintain reverse synchronization.

`NativeLibraryPortable.h` and `LibraryBackup.h` export versioned portable JSON and ZIP archives; complete graphs include unused components and linked Fashion dependencies. Legacy monolithic JSON remains an import boundary only. Restore previews selections, protects references, creates a recovery ZIP and a verified native online backup under `backups/recovery/`, then commits changes. Keep full database backup/recovery distinct from portable interchange; the native copy is for recovery and the ZIP is selective.

### Storage paths and cache ownership

`StoragePaths.h` defines the shared directory layout. The four settings/session/UI JSON files live in `config/`; pinned achievement state and login timestamps live in `library/`. Existing destination files win. Valid root-level JSON is byte-verified, archived under `backups/migration/`, staged, then published without replacing a destination. Failed or malformed migrations retain the original path. Portable ZIP entry names remain unchanged for compatibility; backup reads and restore writes resolve the same canonical paths.

`cache/cache.db` uses independent application identity and schema versioning. The achievement progress repository owns typed account snapshots, progress records and completed bit rows. Full account names are keys; legacy slug files are imported only when their embedded identity matches. Transactions replace one account at a time, reject older fetch timestamps and retain the previous committed snapshot on failure. SQL runs at existing persistence boundaries, not on every render frame. Connections are short-lived and serialized; current journal settings remain DELETE/FULL pending concurrency measurements. A corrupt or foreign cache is reported rather than silently overwritten; close the addon before deleting the rebuildable cache DB.

Cache schema v2 also stores achievement definitions, ordered bits/flags/prerequisites, groups, categories and ordered membership, search names (obsolete hero challenge metadata removed in v14 and waypoint mappings in v15). Reference freshness is dataset-scoped. The established UI projections are reconstructed in bulk; JSON is a transient codec and legacy import boundary only. Cache schema v3 adds shared skin metadata, subtype/weight, restrictions, flags, ordered dye materials and exact-account ownership snapshots. Fashion and Skinventory keep separate in-memory projections and completeness markers but write the same authoritative relational skin records; narrower responses cannot remove the other projection's fields. Legacy skin and ownership files are read only at migration. Cache schema v4 stores the Skinventory item map, many-to-many candidate relationships, vendor costs, normalized item price observations and per-skin verified cheapest-choice references. Failed refreshes preserve previous prices; TTL still governs retries. The current fetch engine persists selected winners rather than every candidate observation. Other public reference/account snapshots remain JSON under `cache/`, with textures and wiki images moved to `cache/textures/` and `cache/wiki_images/`. Legacy rebuildable files move only when a canonical destination is absent. Further relational public metadata migration and cache diagnostics remain outstanding. User pins, preferences, manual progress and saved library records must survive cache deletion. Keep textures, fonts and portraits as ordinary files; do not store large JSON documents as opaque SQLite payloads. Vendored SQLite update procedure: [lib/sqlite/README.md](../lib/sqlite/README.md).

## Presentation and resources

The bundled Inter font and its OFL notice are embedded Windows resources. Custom fonts use the Nexus file registration API. The default font path leaves the ambient Nexus font unchanged. Preserve exact stored fields when presenting or editing incomplete imported data; Cancel must not persist edits.

Fixed profession, specialization, crafting and status icons are version-controlled in `assets/icons/` and embedded offline during compilation. The manifest records provenance and hashes; CI checks linked resource bytes. Update artwork only through explicit reviewed maintenance. Item, skin and skill artwork uses a persistent runtime cache. Do not reintroduce removed raid/strike banner artwork unless explicitly requested.

Achievement names and definitions are retrieved directly from ArenaNet. The legacy single-achievement waypoint catalog is retired; no externally hosted achievement dataset is required.

AE2 interchange is separate from the internal native data model: see [shared build specification](shared-build-spec.md) and the vendored JavaScript reference implementation in `lib/alter-ego-build/`.

## Release precautions

Keep the experimental branch separate from main until explicitly approved. Before merging, validate real-library migration, restart, component editing and comparison, imports, Fashion, ZIP restore and normal in-game behavior. CI compilation and unit tests do not replace in-game validation.

### Explicit component consolidation

The Components detail pane offers exact duplicate consolidation into the selected survivor, with affected Loadout names and confirmation. The native transaction revalidates equality, revision and skill profession compatibility before rewriting references and deleting the redundant record. Independent duplicates remain valid until explicitly consolidated. Usage counts are indexed per library revision; existing editor drafts reject a changed library revision rather than overwriting newly saved data.

Private Copy & Edit offers explicit reuse of an exact compatible component, verified again in the native transaction against the current revision and original reference. Shared edits and intentional duplicates preserve their identity; exact matches are disclosed rather than silently consolidated. Private Base Build editing cannot change the profession of an already referenced Loadout.

Cache schema v5 stores specializations, ordered minor/major trait IDs, traits, skills, ordered profession membership, item stats and ordered attribute names, and dyes with native RGB channels for each material. Only the API's heterogeneous tooltip facts remain per-record JSON. ReferenceMetadataCache owns atomic snapshot replacement, stale-capture rejection, native-first legacy migration and bulk projections; no network policy changes. Item metadata, item names, character/Vault/Clears snapshots and wiki data remain to be evaluated separately.

Cache schema v6 consolidates item details and Commerce item names in reference_items; the complete flag distinguishes a public detail fetch from a name-only record. Commerce owns candidate membership and pricing, not a second name table. Exact name-to-ID aliases remain a separate relational lookup to preserve selected IDs for ambiguous names and historical spellings. Full details take precedence over narrower Commerce names. Type-specific item details remain an API extension field; typed common metadata is authoritative. Item/name JSON is legacy migration input only. SaveItemNameCache clears its dirty flag only after a successful commit of the same in-memory snapshot.

Storage & Cache diagnostics are available in Nexus addon options on explicit inspection. A read-only SQLite connection checks identity, schema, quick integrity and foreign keys, and reports database sizes, reference counts and freshness plus downloaded artwork size. Diagnostics do not create, migrate, repair, delete, or fetch anything. All-cache rebuilding remains a game-closed operation; selective live invalidation requires coordination with in-memory projections and workers.

Native graph merges reuse a colliding ID only when both name and exact payload match; Skills additionally require independently verified matching professions. Conflicts are remapped without consuming another incoming component's original ID. Unused independent components remain intact.

Aggregate Loadout edits enforce the same profession guard as private and shared Base Build edits: create a new Loadout to change profession. Legacy migration never deduplicates Skills with missing profession context, even if their payload is identical.

Cache schema v7 moves the character projection to typed character, crafting, equipment, ordered upgrade/infusion/dye, attribute, tab-name, build/skill/spec/pet/legend/weapon records (obsolete hero-point records removed in v14). Exact account and character identities distinguish unknown-account legacy rows. Native presence wins over legacy JSON, including empty snapshots. Capture and write are serialized; a full projection is replaced atomically at the existing persistence boundary. This first pass retains aggregate roster reconciliation; incremental per-character SQL updates, account-response ownership and worker lifecycle still require audit. Newly supported pet, legend, weapon and binding fields retain missing-field markers rather than inventing known data. No refresh policy change.

Cache schema v8 replaces sanitized Clears and Wizard's Vault filenames with independently keyed exact-account snapshots, typed section/entry/bit and period/objective rows, and season metadata. Existing reset filtering and request scheduling remain in Clears.cpp. Persist original legacy snapshots before reset filtering; require an embedded matching identity for scoped legacy files and verified single-account context for old unscoped input. Writes are serialized and transactional; older dataset timestamps are rejected. Runtime cache loading rechecks the represented account before publishing. Diagnostics includes both datasets. Per-section source freshness and late callback generation checks remain future work.

### One-shot worker ownership

`BackgroundWorkers.h` owns the joinable one-shot jobs previously detached in GW2API, Clears, Skinventory, Commerce, achievement metadata, relay and website imports. Completed handles are reaped on launch. The lifecycle owner opens the registry during load, closes admission before deregistering callbacks and joins all jobs before persistence and subsystem teardown. Domain busy-state failure handlers run outside the registry lock; cancellation is cooperative and exceptions do not escape the worker entry point. Large aggregate fetches check cancellation at batch boundaries. WinINet read helpers reject truncated responses and use the existing 12-second operation timeout across clients. This is not a hard total network deadline; DNS/proxy resolution and synchronous external callbacks still require runtime validation. Icon and WikiImage retain their existing owned queue workers. Font release is outside the font mutex; callback deregistration semantics and full account-generation validation remain outstanding. No request scheduling, retry cadence or startup policy changes.

Only explicit verified account rosters authorize pruning. Registry-only fast paths no longer authorize deletion. Character reads use immutable revision-cached shared projections; account and pending-list reads return copies. Critical partial or malformed replies do not replace the previous character. Exact account and character identity governs replacement and crafting reuse. No refresh cadence or schema change.

Completed character refreshes serialize only the exact account/name record once a native snapshot exists. Incremental SQL replaces that character and its children in one transaction, retaining its row ID and order, rejecting older per-character freshness and leaving other records intact. Only the first snapshot retains the aggregate transaction. Verified roster deletion uses a targeted account-scoped transaction, commits before publishing the removal, and retains previous rows on failure. A failed baseline inspection fails closed. No schema version change.

### Startup cache maintenance

The Storage & Cache options schedule an exclusive, fixed-operation request under `config/cache-maintenance-request`. On next startup, before subsystem initialization or background jobs, `CacheMaintenance.h` consumes the request and either quarantines the entire cache directory (including damaged DB and sidecars), archives artwork and failure markers while retaining wiki acquisition metadata, or invalidates one relational dataset group in a transaction after archiving known legacy sources. Public catalogs and Commerce share item identity and are invalidated together. Account progress includes Clears, Vault, owned skins and achievement progress; durable pins are separate. Normal fetch paths rebuild data without changing their cadence. Moved files remain under `backups/cache-quarantine`; partial failure is reported rather than silently deleting or retrying against newly rebuilt data. No durable library, configuration, login history or recovery backup is removed. This is restart-only, not live eviction.

The dedicated IconManager and WikiImage queue threads close admission and notify before addon deregistration; all one-shot jobs and both queues are joined before API teardown. Queue exceptions and cancellation release loading markers without treating shutdown as a confirmed remote failure. Worker audit covered all runtime translation units; external callback quiescence is a separate open workstream.

### External callback admission

`CallbackLifetime.h` provides a shared local admission gate for render/options, input, Nexus events (including Skinventory) and font callbacks. Close admission before deregistration, then drain admitted bodies before worker join and state teardown. The gate mutex is never held across callback bodies or host calls, including synchronous reentry. This does not serialize concurrent admitted bodies or prove host deregistration quiescence: Nexus must not call into unmapped DLL code. Close-on-escape is a registered raw pointer, and texture loads with null callback depend on the host's resource ownership. Unload must not be invoked reentrantly from an admitted callback; the host lifecycle contract and in-game behavior remain to be verified.

Cache schema v9 stores wiki acquisition metadata and skin/currency failure timestamps in separate typed tables. WikiMetadataCache owns native-first legacy migration and transactional snapshots with independent presence markers. WikiImage retains in-memory projections; no render-time SQL was added. Startup artwork reset preserves acquisition metadata and empties only negative-cache records, retaining the authoritative empty marker. Existing image bytes remain ordinary files. No network retry policy changed.

`AccountIdentity.h` defines exact account/character identities and a shared reply matcher. Echoed account names must match; old non-echoing responses are accepted only with verified single-account context. Skinventory distinguishes full API and batch ownership requests, verifies endpoint and captured account epoch before publishing, validates complete requested batch ID sets, and keeps partial batch results separate until completion. The opportunistic fashion unlock map is invalidated when the logged-in account changes. Clears, Vault and achievement replies check the represented account under publication mutexes and cap response array access. Further typed selection and completion correlation remain open.

## Native account retrieval

`config/accounts.db` is a durable account registry keyed by ArenaNet GUID. Windows Credential Manager stores keys separately from exportable data. Native character, skin ownership, account achievement, Clears and Vault consumers use the account GUID, owned workers and direct typed results, using native authenticated requests. Character equipment/build tabs are retrieved in bulk; complete successful character snapshots replace only the corresponding identity. Verified same-character legacy rows may be superseded by a fresh GUID record. The Library remains shared and account-independent. Native inventory and roster tables in cache schema 10 are scoped by GUID. The full account achievement response is shared by overlapping consumers and replaces the account progress snapshot; category selection must not repeatedly download it. Daily/weekly Vault rollover validation remains in Clears. Keys are entered explicitly in Nexus options; no external credentials are imported. In-game and independent freshness validation remain required.

Cache schema 11 adds independent wallet balances/currency definitions, guild leader access and globally GUID-keyed guild bank slots/coins, and public item binding flags. Personal loose-stock availability excludes guild, equipped, armory, delivery, stale and failed rows; missing stat selection is not a verified match. Inventory owns an immutable item/location index; Compare's exact-ID acquisition aid does not alter semantic equality. Shopping subtracts only fresh loose items mapped uniquely to one locked skin by the known acquisition catalog. Remaining totals are conditional on actual game eligibility. Wallet and guild views use separate queries; optional automatic inventory refresh uses 30-minute TTLs (60 minutes for roster and legendary armory) and a minimum 30-minute attempted-request cooldown, only for the visible selected account. Manual refresh bypasses these intervals. No search/filter-triggered requests.

Automatic API refresh has a master opt-in and durable per-dataset inclusion mask in settings.json. Character, achievements, skin ownership, public catalog, Clears, Vault and each inventory storage have independent gates. Manual actions bypass inclusion gates. ArenaNetAdmission provides one active request, FIFO admission of up to 64 waiting callers, bounded 120-second wait and cooperative unload cancellation. Existing rate limits remain shared. This is admission control, not a fully deduplicated priority scheduler.

Vault cache schema 12 gives each daily, weekly and special section its own confirmed timestamp. Verified responses publish independently; failure, rate limit, reset-held or missing responses preserve the other periods. A transactional merge retains older rollover fingerprints for invalidated sections and rejects late older period writes. Automatic entry/reset/retry checks select stale unclaimed or unverified periods; explicit Refresh still requests all three. The footer uses the oldest verified section timestamp only when all three have data; per-period ages appear in status detail. This does not yet separate Clears persistence.

Cache schema 13 adds nullable remaining charges to character equipment; older rows remain unknown, explicit zero survives round-trip. Character-wide gathering/fishing/Jade Bot items from the existing supplemental equipment response are normalized to tab zero, independent of template selection. Existing character item/skin metadata batching includes these rows. No additional authenticated requests or durable library schema changes.

### Public upgrade and Vault reference catalogs
Cache v16 adds the discovered public item ID index, typed upgrade membership (canonical item details remain in reference_items), and public Vault definitions keyed by objective ID. The existing Commerce full scan captures upgrades in the same pass. Subsequent equipment refreshes fetch the public ID index, new IDs, and known upgrades in batches, sharing Commerce's in-flight gate. Public Vault definitions are separate from account completion. UI reads immutable snapshots; network work stays on joinable workers. Legacy curated upgrade identities remain a temporary offline bootstrap without old effect text. Account Vault data remains authoritative if a public definition conflicts. The exact infusion picker uses typed infusion/enrichment membership (amulet selects enrichment); newly refreshed equipment IDs are available to imports without an addon restart. Wiki and public API probes are explicit manual workflow options.

Old experimental picker values are interpreted for display only; saved records are not bulk-rewritten. ### Wiki resource freshness policy

Keep public ArenaNet catalogs in the existing SQLite cache. Wiki reference datasets have a separate build-time resource policy, not an account refresh policy. The default is 24 hours between build-time refresh attempts per dataset, including failed attempts. A normal build with a fresh resource makes no Wiki requests. Persist last-success and last-attempt timestamps across builds; retain validated last-known-good snapshots in source control, including provenance and schema version. A transient CI cache alone is not a durable fallback. Only publish replacement snapshots after complete validation; failed or incomplete retrieval must not overwrite good data or prevent offline compilation. Use a suitable structured Semantic MediaWiki JSON query or MediaWiki JSON API first, direct HTML scraping only on primary failure. Normalize the relevant fields instead of embedding whole pages. Explicit refresh/diagnostic is opt-in.

| Resource class | Policy |
| --- | --- |
| Wiki world boss and meta-event schedules, raid bounty and fractal rotations/scales, Emboldened/Call of the Mists, specialization descriptions, static festival reference mappings | Build-time, 24 hours per dataset; event timers also runtime 30 days |
| Wiki skin acquisition and vendor/currency reference information | Target build-time 24-hour reference metadata only where a bounded, verified bulk source exists; otherwise retain on-demand SQLite caching and use a 30-day per-record success age. Do not crawl individual pages for every skin or embed gallery images. |
| Wiki active special/bonus events | Existing runtime six-hour check; keep separate because events can be announced after a DLL release |
| ArenaNet new item/skin ID discovery and public Vault definitions | Runtime seven-day check |
| ArenaNet known upgrade definitions, pets, legends, item stats and dyes | Runtime 30-day refresh |
| Account progress, prices and ownership | Existing independent live/account-specific refresh policies; not build assets |
| Fixed art and curated recommendations | Manual/version-controlled |

Currency scope: the existing WikiImage path resolves currency artwork URLs and skin vendor costs; it is not a comprehensive currency acquisition catalog. Ordinary game currency identities and icons should use ArenaNet metadata where available. Keep large skin images and remaining Wiki-only currency artwork demand-loaded; validate any compact reference dataset separately. Bulk skin/currency query completeness, source licensing/attribution, and runtime fallback consumers must be verified before enabling automatic retrieval or distribution.

The first implemented Wiki resource group externalizes raid bounty and fractal rotation/scale facts into a version-controlled bootstrap snapshot. Build-only generator produces C++ table initializers, and CI caches per-dataset attempt/success markers with a source-controlled offline fallback. Offline tests use the checked-in baseline; newly retrieved data must pass structural checks, cross-check recommended scale names, and retain a verified raid date anchor before it can be consumed. The CI artifact includes the selected snapshot for review/promotion; cache eviction can revert to the checked-in baseline. Other sources in the manifest are intentionally disabled pending live schema and completeness verification. Initially no new runtime Wiki requests were introduced.

The 2026-11-25 Debian bootstrap confirmed the live wikitext payloads for raid and fractal templates and the nested event timer JSON (v5.4). Schedule parsing now uses wikitext first, validates the bidirectional scale map and exact timer phase names, and generates offline Vault daily starts for 27 matched phases. The snapshot is seeded with verified data; a newer checked-in successful snapshot supersedes old CI state. Removed one-time forced bootstrap retry; ordinary builds now observe the 24-hour attempt age. Weekly raid effect pages only transclude templates; their underlying rotation templates still need verification. Skin/currency bulk sources remain disabled.

Cache v18: Wiki event timers are the first hybrid resource. The build generator emits shared exact phase identities, verified timestamp and baseline starts; the runtime C++ parser reads the same public JSON schema. Startup selects the newest valid snapshot and persists a newer baseline into relational SQLite rows (equal timestamps favor existing cache). A manual refresh or opted-in automatic startup/Vault-entry check after 30 days uses MediaWiki JSON first and direct raw JSON only on failure, with 24-hour failed-attempt backoff, one joinable worker, no account identifiers or credentials. ### Wiki data provenance and rights

Keep the addon MIT license separate from third-party source rights. The current normalized schedule resources contain selected factual names, numeric scale/rotation assignments and start times, not copied Wiki prose or source templates. [Third-party notices](../THIRD_PARTY_NOTICES.txt) is the authoritative distribution attribution for both embedded and runtime reference data. Record the exact source page(s), verified snapshot provenance and applicable terms for every new resource; preserve that information when promoting a snapshot. Where available, record the source revision for traceability. Original Wiki contributor expression is subject to GFDL 1.3 or later; game-owned content has separate rights. Factual extraction alone is not a blanket clearance of database/compilation rights or source terms. Keep new resources disabled until scope, provenance and reuse rights have been reviewed. In particular, prefer factual structured fields or independently authored specialization summaries; copied descriptions require a separate rights and GFDL compliance review before distribution. Update the notices for newly enabled datasets and retain them with source and binary releases.

Cache v19 records per-skin acquisition success and attempt times separately from artwork. Explicit skin selection queues eligible acquisition retrieval on the existing owned Wiki worker even when the image is cached; no bulk scan or filter-triggered requests. Success eligibility is 30 days, failed attempts back off 24 hours across restarts. Older rows remain visible but unverified until selected. Only validated, nonempty acquisition results and their verification time commit together; incomplete extractions retain previous fields and success age. Artwork invalidation resets failed acquisition attempts, not successful data. Active special events keep a six-hour success TTL and 60-minute attempt cooldown in the atomic disk wrapper; while Achievements is open, recheck on expiry and use stale dated windows on failure without claiming expired events are current. No new automatic Wiki datasets.

### Unified freshness engine (first implementation pass)

RefreshEngine.h is the common policy foundation for interval, attempt age, manual override, reset minimum epoch, stable 0–45 second recurring spread and pre-dispatch metadata ID claims. Nexus Objective tracking defaults to 15 minutes (5–60 configurable) for pinned achievements, Clears and daily/weekly Vault; general achievement browsing and Special remain 30 minutes. NativeProgress owns a credential-generation-aware, account-keyed shared in-memory achievement response and ordinary 15-minute failure cooldown. A new consumer can adopt a shared response rather than querying again. Manual calls bypass that cooldown and freshness but coalesce overlapping successful work. Clears requires a post-reset snapshot; existing public category rollover verification stays unchanged. Vault checks periodically when visible, preserves claimed-section skip and reset retry paths, and tracks attempt cooldown per account and section. Public season metadata has separate session-wide 24-hour eligibility and end-date invalidation. Armory matches the 30-minute inventory TTL. Metadata async wrappers claim missing IDs before creating workers, sharing achievement definition claims between pinned and category retrieval; ordinary reattempt is delayed 15 minutes. Synchronous metadata import paths, durable attempt state, full activity scheduling, shared Clears public definitions, broader transport priority/rate and diagnostics remain tracked in the roadmap; do not describe the foundation as full migration.

Clears ordinary definition retrieval reuses still-current daily/weekly rows; manual Refresh forces all categories and progress, and the visible scheduler recovers missing weekly definitions even if the reset was observed on another tab. Ordinary failures back off 15 minutes, with existing daily rollover retries unchanged. Vault season metadata eligibility is evaluated independently of whether any account section is due.

Approved character integration rule: automatic offline reconciliation waits at least 600 seconds from the last observed active time (including confirmed logout). A login resumes active timing; never finalize a previous logout while the character is active. Keep a persisted per-scope activity coverage watermark independent of the latest retrieval timestamp; an explicit early manual refresh can update visible data but cannot clear pending logout reconciliation. Only a verified request started after the grace, with no subsequent character activity, may finalize that logout. The pure RefreshEngine helpers encode these boundaries; the actual activity scheduler and persistence remain pending.

Character activity integration: the 10-minute active interval is demand-driven, not a background poll. Nexus gameplay/identity observations are local once per second, with 12-second transition debounce, including while hidden. Account GUID and character activity plus per-scope attempt/success/coverage persist atomically in config/character_activity.json every 30 seconds and on unload. Active session is not restored across restart. Old cached records with no observed activity remain usable; external play is not inferred. Characters/Compare use the selected target (Characters also the active character in context), Inventory Items and Shopping request due scopes only while visible. Inventory schedules one scope at a time, at least five seconds between automatic jobs, active bags/equipment first; All Accounts auto-refreshes only the verified active account. Account storage uses a 30-minute active interval and offline reconciliation; roster 24h; delivery remains time-based. Physical equipment uses one pinned schema and shared session broker; validated physical slots commit separately from the all-tab character snapshot. Manual bypasses ordinary cooldown and grace, but only a post-grace offline request can cover logout. Core/build/crafting still retrieved as one character snapshot; independent sub-scope freshness and external activity detection remain follow-ups.

Specialization opt-in governs both the character snapshot and physical equipment scope. The physical broker only marks Inventory current after validated storage commit; an otherwise useful raw response cannot advance inventory freshness on parse or storage failure. Inventory filters do not change automatic demand. Compare only requests acquisition scopes when there is a selected target.

API Activity diagnostics record actual WinINet call attempts for the fixed ArenaNet transport and Wiki GET/download paths, including failed sends and incomplete reads. Only fixed endpoint groups, counts and monotonic-second buckets are retained in process memory. HTTP completion is separate from dataset validation. Storage & Cache samples once per second only while the tree is open; achievement broker cache reuse and overlapping successful work are counted separately. Runtime Wiki GETs and downloads share bounded, cancellation-aware admission and one-second start spacing; HTTP 429 holds new Wiki admission for at least 60 seconds. Startup raid icon prefetch uses a managed worker. This does not yet deduplicate all Wiki resources or tag every initiation reason.

Fixed raid modifier artwork (Emboldened and Call of the Mists) uses reserved resource IDs 9300001/9300002 and IconManager. The checked-in 32x32 RGBA originals are sufficient for the 16/19px Clears layouts. Both views use embedded resources; no startup Wiki prefetch for these icons. Manual staging retains reviewed originals. The earlier startup worker was superseded.

IconManager now uses HttpClient for dynamic artwork, including ArenaNet render host diagnostics and the shared Wiki gate. Actual linked RCDATA existence blocks both disk and HTTP fallback even while Nexus texture creation is pending; unknown IDs remain demand-loadable. Verified image bytes publish atomically. A separate cache/textures/failed_icons.txt ledger persists failed artwork HTTP attempts for seven days (local texture publication retains a short session cooldown). Positive cached images are indefinite. Scribe retains identical pixels and ICC profile after removing text metadata.

Companion artwork: the reviewed ArenaNet snapshot includes all eight legend swap skill icons (existing 5000000 + skill ID) and all 67 pet icons (9400000 + pet ID). Assets are 64x64 RGBA PNGs, checked by the generator and actual PE resource verification. Legend rendering already uses the skill IDs; the pet picker shows the icons without changing selection semantics. Public legend/pet catalog definitions remain runtime cached, independent of artwork. Normal builds do not download companion artwork.

Cache v20 separates verified account achievement snapshots (including bits and exact GUID) from the UI projection that may contain optimistic or synthetic progress. The shared NativeProgress broker loads verified snapshots on worker demand, revalidates current credentials and progression permission, enforces age/reset eligibility and commits validated responses before publishing. Existing projections are not promoted to verified snapshots. Public Vault season has a separate singleton verified-at/end row in the same rebuildable cache, consulted on worker demand with a 24-hour maximum age and end-date invalidation. Manual requests bypass freshness; invalid or failed writes retain previous verified rows. Account-progress maintenance invalidates raw and projected account data; Public Catalog maintenance invalidates public season metadata. UI projection, rollover and in-game behavior still require validation.
